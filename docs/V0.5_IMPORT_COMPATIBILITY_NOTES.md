# EQ Library v0.5 — import/export compatibility notes

Status: approved v0.5 product behavior. This document supplements `CHATGPT_PROJECT_RUNBOOK.md`, `ARCHITECTURE.md`, and `V0.5_KT02H20_IMPLEMENTATION_PLAN.md` for file-import compatibility and fidelity wording.

## Core rule

File export and Direct Flash are separate delivery paths. A limitation in a third-party importer must not remove a valid EQ Library Direct Flash path, and EQ Library must never silently clamp or rewrite canonical EQ values merely to satisfy an importer.

Use these terms consistently:

- **Add to My EQs / Save** — persist the output-specific selection locally in EQ Library.
- **Export** — create a verified file format for an external app/importer.
- **Direct Flash** — explicitly write the derived EQ plan to a supported DAC over USB after confirmation.
- **Saved to device / persists** — say this only when device persistence is established for that hardware path.

## TRN Black Pearl AutoEq text

Black Pearl remains both file-capable and Direct-Flash-capable. Both paths derive from the same shared ten-band Black Pearl hardware representation, but file serialization follows the verified `cheesyserg/pyBlackPearl` AutoEq import contract.

The exported text is:

```text
Preamp: -6.00 dB
Filter 1: ON LS Fc 105 Hz Gain 4.00 dB Q 0.750
Filter 2: ON PK Fc 1000 Hz Gain -2.50 dB Q 1.250
Filter 3: ON HS Fc 8000 Hz Gain -1.50 dB Q 0.750
```

Black Pearl-specific type tokens are:

- Peak → `PK`
- Low Shelf → `LS`
- High Shelf → `HS`

Do not use generic `LSC` / `HSC` shelf tokens in the Black Pearl file serializer. They are valid in other AutoEq/Equalizer APO-style contexts but are not parsed correctly by the verified pyBlackPearl shelf importer.

The reviewed pyBlackPearl importer accepts `Preamp:` and up to ten filters. It limits imported preamp to approximately `-16 dB..+6 dB`. EQ Library does **not** pre-clamp to that range. If the real Black Pearl plan requires, for example, `-18 dB`, export the true `-18 dB` value and disclose that pyBlackPearl will limit it on import. Direct Flash remains independently available when the actual hardware plan passes Black Pearl safety/representability checks.

`cheesyserg/BlackPearlControl-Android` is not a generic compatibility target for shelf-bearing files: its reviewed importer hard-codes imported filters as Peak. Do not change EQ Library output acoustics to accommodate that limitation and do not claim compatibility with every third-party Black Pearl controller.

## TOPPING Tune

TOPPING Tune is a selectable **Apps** output, not a Direct Flash hardware target in v0.5.

Product presentation:

`TOPPING Tune — .txt · AutoEq parametric · 10 bands`

Current official TOPPING material documents:

- direct AutoEq import through TOPPING Tune;
- up to ten EQ bands;
- preamplification range `±12 dB`;
- per-filter gain range `±12 dB`;
- Q range `0.1..15`;
- Peaking, Low-shelf, and High-shelf filter types among the supported PEQ types;
- direct numeric entry for frequency, gain, and Q.

EQ Library exports standard AutoEq-style `PK / LSC / HSC` parametric text for this path. Over-budget/unrepresentable canonical EQs use the shared complete-response finite-target fitter; never take the first ten source bands merely to create a TOPPING Tune file. Source preamp is not silently clamped to the documented Tune range.

TOPPING's public guide does **not** establish the downstream device storage quantization applied after Tune imports a file. Therefore v0.5 must not invent hardware precision or claim Exact target fidelity from an assumed frequency/gain/Q step. The product-facing Tune file adapter uses only deterministic EQ Library text serialization precision for file generation and conservatively reports the result as **Optimized** until Tune/device import precision is independently qualified. This does not mean a material acoustic fit necessarily occurred; it means Exact downstream preservation is not yet proven.

Hidden/nonselectable TOPPING DX5 II / DX1 II registry/reference entries are not Direct Flash support and must not be exposed as physically qualified hardware outputs.

## FiiO JA11 and stock JCALLY JM12 file formats

The current v0.5 investigation did not establish a sufficiently verified local preset-file interchange contract for either device. Therefore:

- FiiO JA11 remains a hardware-only five-band **Direct Flash** output in EQ Library.
- Stock JCALLY JM12 remains a hardware-only five-band **Direct Flash** output in EQ Library.
- Do not invent `.txt`, JSON, binary, or other preset files for either device.
- A future verified import/export format may be added **alongside** Direct Flash; it must never replace the existing Direct Flash feature merely because file support is added.

JA11's observed Direct Flash transaction includes Apply and the run-mode Save command, followed by verification; physical qualification is still pending.

Stock JM12 has no independently corroborated explicit run-mode Save command. Live write/readback is implemented, but persistence across unplug/full power cycle remains a hardware qualification question and must not be claimed early.

## Fidelity wording

Finite-hardware fidelity explanations are target-adaptation metadata, separate from source/catalog descriptions.

Use concise reasons such as:

- `Exact · source values preserved`
- `Optimized · native hardware rounding only`
- `Optimized · 14 → 10 bands · full-response fit`
- `Optimized · generated headroom −3.0 dB`
- combine reasons when more than one applies.

Do not force redundant `N → N bands` wording when no band-budget change occurred.

Generated target-specific headroom is always **Optimized**, even if every source filter itself lands exactly on target quantization. This is because the source did not author that playback-gain value.

Native hardware rounding is distinct from response fitting. A profile that only needs native rounding should preserve its source band structure rather than unnecessarily invoking the response fitter.

## Validation requirements

Automated regression coverage for this work must verify at least:

- Black Pearl `PK / LS / HS` file syntax and shelf correctness;
- Black Pearl file/Direct-Flash derived-plan parity;
- true Black Pearl preamp export plus pyBlackPearl importer-side range warning without app-side clamp;
- generated hardware headroom cannot report Exact;
- native rounding is distinguished from full-response fitting;
- deterministic complete-response fitting and source immutability;
- TOPPING Tune standard AutoEq syntax, ten-band fitting, no source-preamp clamp, and conservative precision-pending fidelity;
- JA11/JM12 remain fileless hardware outputs while Direct Flash remains intact;
- JM12 persistence remains pending until the physical checklist establishes it.

Any behavior-affecting change in these paths invalidates the previous signed v0.5 candidate and requires a new exact-source automated/signing candidate before physical hardware qualification.
