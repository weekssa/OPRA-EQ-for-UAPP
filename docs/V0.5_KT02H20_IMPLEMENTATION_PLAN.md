# EQ Library v0.5.0 — KT02H20 Direct Flash implementation plan

Status: approved design, implementation in progress. Hardware qualification pending for both physical devices.

## Scope

v0.5.0 adds separately selectable hardware-output support for:

- FiiO JA11 on its normal FiiO firmware;
- JCALLY JM12 on its stock firmware.

Both devices are treated as five-band PEQ targets sharing a deterministic response-fitting layer where appropriate, while retaining separate USB identity, capability, protocol, transport, validation, and qualification records.

No firmware update, bootloader, cross-flash, account, FiiO cloud/share-code, or unrelated DAC-control functionality is in scope.

## Approved UX

### Settings → Outputs

Add separate output rows:

- **FiiO JA11** — `5-band PEQ with optional direct Flash from My EQs`
- **JCALLY JM12** — `5-band PEQ with optional direct Flash from My EQs`

Each device has its own **Enable direct Flash** toggle, OFF by default. Until its physical checklist passes, show **Hardware validation pending** in the device-specific settings section.

### Active output behavior

JA11 and JM12 are independent output contexts. Selecting either changes output-specific My EQs membership, capability classification, generated hardware representation, connection controls, and Flash availability. It never filters otherwise valid canonical EQs from EQ Library.

### Capability labels

- **Exact** — source uses no more than five compatible filters and every relevant parameter can be represented without target-side acoustic alteration.
- **Optimized** — source response is deterministically fitted to at most five target-compatible filters and the result meets the qualified response-error threshold.
- **Not suitable** — a safe/faithful five-band representation cannot be produced within the device capability profile.

For Optimized profiles use concise copy such as: `Adapted to the device’s 5-band PEQ to closely match the original EQ response.` Never describe this as taking the first five source bands.

### My EQs hardware controls

When one of these devices is the active output and its Direct Flash option is enabled, show one compact device row:

`Connect / Connected` + `Reset EQ to flat`

Reset is disabled while disconnected.

Each saved flashable profile shows **Flash**. Flash is always explicit and confirmed; Add/Save never automatically writes hardware.

### Flash confirmation

Confirmation identifies the target device, whether the representation is Exact or Optimized, and the global EQ/preamp value that will be written when nonzero. It states that the current PEQ will be replaced and saved to the device and that unrelated DAC settings will not be changed.

### Reset confirmation

Reset states that all five PEQ bands and the EQ-related global preamp will be returned to flat/neutral state, listening volume may change, the result will be persisted, and unrelated DAC settings will not be changed. Reset is a device action only; it never creates a canonical EQ, My EQs entry, Favorite, or export file.

## Five-band optimization

The canonical source EQ remains unchanged and complete.

When more than five bands are required, the target converter:

1. evaluates the complete source frequency response using the same supported parametric filter semantics as canonical conversion;
2. fits a deterministic set of no more than five target-compatible Peak/Low Shelf/High Shelf filters inside device limits;
3. keeps source preamp separate from the fit and maps it to the device global EQ/preamp control when representable; when source preamp is absent, separately generated EQ Library safety headroom may be used according to current canonical rules;
4. evaluates response error over a fixed log-frequency grid;
5. returns Optimized only when the candidate meets the tested acceptance threshold; otherwise returns Not suitable.

Do not use preamp as an optimizer degree of freedom for hiding response-fit error. Do not silently clamp source values or mutate canonical source data.

The optimizer must be deterministic: the same canonical source and target capability profile must produce the same bands, global gain, fidelity state, and error metrics.

## Hardware protocol boundary

### FiiO JA11

Initial device identity is limited to the validated JA11 USB identity/behavior. The implementation may use documented observable KT02H20 HID behavior for PEQ/global gain/apply/save/readback but must be independently written in Kotlin.

### JCALLY JM12

Support targets the stock JM12 firmware/hardware interface. JA11 firmware is not required and is never installed, suggested, or invoked by EQ Library. Keep JM12 identity/protocol code separable from JA11 so physical testing can establish differences without coupling the two devices.

### Shared rules

- strict wrong-device protection;
- never connect to an arbitrary KT02H20-family dongle merely because the chipset appears compatible;
- no firmware-update or bootloader commands in the Android implementation;
- no writes to DAC reconstruction filter, amplifier mode, USB mode, balance, microphone, or other unrelated controls;
- unused PEQ slots are explicitly bypassed/disabled when supported, otherwise written to a validated flat state so stale filters cannot remain active.

## Flash transaction target

Preferred verified transaction:

1. identify and connect the exact active-output device;
2. read current five-band PEQ state and global EQ/preamp;
3. build and fully validate the intended target representation before any write;
4. user confirmation;
5. write all five band states/parameters plus global EQ/preamp as required;
6. apply to RAM;
7. read back and verify intended RAM state;
8. persist/save to device flash;
9. read back again where the device protocol reliably exposes persistent state;
10. report success only after required verification succeeds.

If physical testing demonstrates device-specific readback/persistence semantics, document and adjust that device contract rather than weakening validation for both.

## Software validation before hardware arrives

Require automated coverage for:

- exact <=5-band passthrough;
- deterministic >5-band fitting;
- Peak/Low Shelf/High Shelf response evaluation;
- source preamp and generated-headroom handling;
- boundary/range rejection;
- optimization quality threshold and Not-suitable cases;
- protocol packet encode/decode golden vectors;
- signed-value, frequency, Q, filter-type, and per-band status handling;
- complete five-slot overwrite/disable behavior;
- Apply/save/readback ordering;
- staged failure at every transaction phase;
- wrong-device protection;
- USB permission/disconnect handling;
- Direct Flash OFF behavior;
- Reset-to-flat behavior;
- explicit absence of bootloader/firmware and unrelated-control commands.

Maintain a representative golden optimizer corpus so later algorithm changes cannot silently alter generated hardware presets.

## Hardware qualification gates

Create separate Pixel 9 hands-on checklists for JA11 and stock-firmware JM12. Each must record firmware/version where available, exact candidate SHA, signed APK identity/hash, device USB identity, connection/permission behavior, readback, Peak/Low Shelf/High Shelf, global preamp, exact and optimized Flash, persistence across reconnect/power-cycle, unused-slot clearing, reset-to-flat, wrong-device protection where practical, and unchanged unrelated device settings.

Until a checklist passes, the corresponding output remains **Hardware validation pending** and must not be described as physically qualified or included in a stable release claim.

## Release

Target milestone: **v0.5.0**.

A public v0.5.0 release claiming JA11/JM12 Direct Flash support requires software/release/signing gates plus a physical PASS for each device included as qualified. One device may remain pending if the other qualifies first; do not couple qualification outcomes artificially.
