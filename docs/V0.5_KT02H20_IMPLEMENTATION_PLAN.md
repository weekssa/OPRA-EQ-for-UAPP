# EQ Library v0.5.0 — outputs and Direct Flash implementation plan

Status: approved design implemented in software. Automated validation is required on every candidate. Physical qualification is still pending for FiiO JA11 and stock-firmware JCALLY JM12; for v0.5.0 those hardware gates are explicitly deferred to the next incremental release and are not publication blockers while the outputs remain labeled Hardware validation pending.

This document is the v0.5 authority for the output registry, shared finite-target response adapter, FiiO JA11 Direct Flash, and stock JCALLY JM12 Direct Flash. It supplements `docs/CHATGPT_PROJECT_RUNBOOK.md`, `docs/ARCHITECTURE.md`, and `docs/V0.5_IMPORT_COMPATIBILITY_NOTES.md`. Device-specific wire details remain in the corresponding protocol notes and hands-on checklists.

## Scope

v0.5 expands EQ Library from a small fixed set of output branches into one source-agnostic output framework. The canonical EQ stays complete and immutable; each selected output derives its own deterministic representation.

The selectable output registry groups outputs as **Hardware DACs**, **Apps**, and **Universal formats**. It includes file-capable targets and hardware-only targets without pretending that a hardware protocol is a file format.

v0.5 also adds separately selectable Direct Flash support for:

- **FiiO JA11** on normal FiiO firmware;
- **JCALLY JM12** on stock firmware.

And it adds **TOPPING Tune** as a selectable Apps output using direct AutoEq `.txt` import; TOPPING Tune is not a Direct Flash target in v0.5.

No firmware update, bootloader, cross-flash, account, cloud/share-code, or unrelated DAC-control functionality is in scope.

## Output framework

`ExportDevice` is the single UI/domain registry for output identity and presentation. Each target declares, as applicable:

- display/folder name;
- category;
- file extension/MIME type or hardware-only status;
- output format kind;
- user-facing settings subtitle;
- validation status;
- declared EQ capabilities;
- whether the output is selectable in the current product.

The active output is a global **operating context**, never a canonical-catalog filter. Changing it changes output-specific My EQs membership, conversion/fidelity status, file export, connection controls, and Flash availability. It never hides an otherwise valid canonical EQ from EQ Library.

File-capable outputs may create app-owned artifacts through the Storage Access Framework. Hardware-only outputs do not create invented files; their derived representation remains local until the user explicitly taps **Flash**.

FiiO JA11 and stock JCALLY JM12 remain hardware-only because no sufficiently verified local preset-file interchange contract has been established. Future verified file support may be added alongside Direct Flash; it must not replace or remove Direct Flash.

TOPPING DX5 II / DX1 II remain nonselectable implementation/reference registry entries. Product-facing TOPPING support in v0.5 is the **TOPPING Tune app import** path, not an unqualified hardware Direct Flash claim.

## Shared finite-target response adapter

The shared deterministic adapter is the authoritative derivation path for finite PEQ hardware targets, including:

- TRN Black Pearl — 10 hardware bands;
- FiiO JA11 — 5 hardware bands;
- stock JCALLY JM12 — 5 hardware bands.

The same response machinery may be reused for a finite file/app target such as TOPPING Tune, but app text serialization precision must never be mislabeled as verified downstream hardware quantization.

The historical Kotlin class names containing `Kt02h20` / `FiveBand` are compatibility names only; the algorithm is not logically limited to KT02H20 devices or five bands.

Rules:

1. Keep the canonical source EQ unchanged and complete.
2. Reject unsupported source filter types instead of dropping them.
3. If every source band and source-authored preamp is natively representable at the hardware target's actual quantization, preserve the source as **Exact**.
4. If the source fits the target band structure and ranges but values require only native target rounding, preserve the same filter structure, quantify the final rounded response, and report **Optimized · native hardware rounding only** rather than unnecessarily fitting a different curve.
5. Otherwise evaluate the complete source response and deterministically fit no more than the target's available Peak / Low Shelf / High Shelf bands.
6. Quantize only at the target boundary using the target's declared storage/protocol resolution; for app files, distinguish deterministic text serialization precision from unverified downstream hardware precision.
7. Measure the derived response on a fixed log-frequency grid and return **Optimized** only when RMS and maximum-error gates pass; otherwise return **Not suitable**.
8. Never use preamp as a hidden optimizer degree of freedom and never silently truncate source bands for these finite hardware targets.
9. Never mutate canonical source values, source preamp, creator/provenance, or filter order merely to fit a target.

### Playback gain / missing source preamp

Source-authored preamp remains separate from the response fit and is mapped to the target's playback/global-gain control when representable.

When canonical source preamp is absent, the finite-target adapter derives conservative target-specific safety headroom from the final target response. This derived value is representation metadata only: it must not be written back into canonical `preampGainDb` or used to rewrite canonical `eqLibrarySafetyHeadroomDb`.

A representation that needs target-side rounding, response fitting, or generated safety headroom is **Optimized**, not Exact. Generated headroom is always Optimized even when every filter itself lands exactly on target quantization.

## TRN Black Pearl v0.5 integration

Black Pearl remains independently qualified hardware from the v0.3/v0.4 foundation; v0.5 does not change its USB protocol identity or unrelated-control boundary.

v0.5 changes the derived EQ plan so file export and Direct Flash share the same device representation. In particular:

- profiles above 10 bands are fitted from the **complete source response** rather than taking the first 10 bands;
- values requiring only Black Pearl native rounding preserve the source filter structure and are reported separately from a full-response fit;
- exact protocol-encodable filter values are preserved when natively representable;
- generated playback headroom cannot be labeled Exact;
- finite per-band gains outside the currently validated ±10 dB listening range remain unchanged when wire-encodable and retain the explicit caution/`Flash anyway` gate;
- global playback-gain absolute limits remain blocking and are never clamped;
- Black Pearl confirmation preview consumes the same `BlackPearlFlashPlan` used by the actual Flash transaction so fidelity/gain/warnings cannot be guessed by a separate UI heuristic.

### Black Pearl file import contract

The Black Pearl `.txt` file uses the same derived filters and playback gain as Direct Flash, serialized specifically for the verified pyBlackPearl AutoEq importer:

- Peak → `PK`
- Low Shelf → `LS`
- High Shelf → `HS`

Do not reuse generic `LSC` / `HSC` shelf tokens in this serializer.

pyBlackPearl accepts the AutoEq file and limits imported preamp to approximately `-16 dB..+6 dB`. EQ Library must still export the true derived preamp unchanged and disclose any importer-side adjustment. Never clamp in EQ Library merely to satisfy this importer, and never disable valid Direct Flash because an external importer has a narrower convenience range.

Do not claim generic compatibility with every third-party Black Pearl controller: the reviewed BlackPearlControl-Android importer does not preserve shelf types correctly.

Because v0.5 changes Black Pearl DSP derivation behavior, the v0.5 exact candidate requires a focused Black Pearl regression smoke before release even though the previously qualified transport protocol itself is unchanged.

## TOPPING Tune v0.5 integration

TOPPING Tune appears under **Apps** as:

`TOPPING Tune — .txt · AutoEq parametric · 10 bands`

Current official TOPPING material establishes:

- direct AutoEq import in TOPPING Tune;
- up to 10 EQ bands;
- preamplification range `±12 dB`;
- per-filter gain range `±12 dB`;
- Q range `0.1..15`;
- Peak, Low Shelf, and High Shelf among the supported filter types;
- direct numeric parameter entry.

EQ Library uses standard AutoEq-style `PK / LSC / HSC` text for this target. When a canonical EQ exceeds the ten-band budget or otherwise needs target adaptation, use the complete-response finite-target fitter; never take the first ten source bands. Source preamp outside the documented Tune range is not silently clamped to make a file.

TOPPING's public guide does not establish the downstream device PEQ storage quantization used after import. The product-facing `ToppingTuneFileExport` adapter therefore uses deterministic EQ Library **text serialization precision only** and conservatively reports TOPPING Tune output as **Optimized** until import/storage precision is independently qualified. This is deliberately more cautious than pretending an assumed 1 Hz / 0.1 dB / other step is verified hardware resolution.

## Approved UX

### Settings → Outputs

Outputs are grouped by category. FiiO JA11 and JCALLY JM12 appear as separate hardware targets. Each device has an independent **Direct Flash** toggle, OFF by default. TOPPING Tune appears under Apps and does not expose a Direct Flash toggle.

Until physical qualification passes, JA11 and JM12 show **Hardware validation pending**. JM12 additionally keeps persistence pending wording. Black Pearl must not be relabeled pending merely because the new devices are pending.

### Capability labels

For finite hardware targets:

- **Exact** — the canonical EQ is natively representable at the target's actual limits and quantization without target-side acoustic alteration or generated headroom.
- **Optimized** — EQ Library deterministically derives a target representation and the result meets fixed quality gates.
- **Not suitable** — a safe/faithful target representation cannot be produced within the declared device capability profile.

Where available, show a concise reason separate from source details:

- `Exact · source values preserved`
- `Optimized · native hardware rounding only`
- `Optimized · 14 → 10 bands · full-response fit`
- `Optimized · generated headroom −3.0 dB`

Never describe an Optimized JA11/JM12/Black Pearl profile as taking the first N source bands.

TOPPING Tune remains conservatively Optimized while its downstream storage precision is unqualified; this precision-pending status is different from saying a full-response fit necessarily occurred.

### My EQs hardware controls

When a hardware target is active and Direct Flash is enabled, show the compact connection/reset row:

`Connect / Connected` + `Reset EQ to flat`

Reset is disabled while disconnected. Every saved flashable profile may expose **Flash**. Add/Save never automatically writes hardware.

Confirmation must use the exact derived plan that the transaction will write. It identifies the device, Exact/Optimized state, EQ-related playback/global gain when applicable, persistence semantics, and any required safety caution.

Use **Add to My EQs / Save** for local membership, **Export** for external files, **Direct Flash** for USB writes, and “saved to device/persists” only where that hardware behavior is established.

## Device protocol boundaries

### FiiO JA11

Strict USB identity:

- VID `0x2972`
- PID `0x0102`
- HID report ID `0x02`

Observed run-mode commands used by EQ Library:

- `0x15` — filter parameters;
- `0x17` — global EQ gain;
- `0x18` — Apply;
- `0x19` — Save.

The five hardware slots support Peak / Low Shelf / High Shelf. The transaction reads existing state, builds/validates the complete target before writes, writes all five slots including flat padding, writes global gain as needed, applies, reads back, saves, and performs final readback. Success is reported only after the required verification completes.

No verified JA11 external preset-file format is exposed in v0.5. This does not remove Direct Flash.

### Stock JCALLY JM12

Strict USB identity:

- VID `0x31B2`
- PID `0x0111`
- HID report ID `0x4B`

Observed run-mode register protocol:

- handshake `0x43`;
- read `0x52`;
- write `0x57`;
- EQ-enable register `0x24`;
- five PEQ bands in registers `0x26..0x2F`;
- digital/global gain register `0x66`.

EQ Library preserves unrelated register bytes and uses a tracked relative EQ Library gain delta so later Flash/Reset operations replace or remove only the app-applied adjustment rather than blindly accumulating changes.

No independently corroborated explicit persist/save command has been established for stock JM12 firmware. The app must therefore say that persistence across a full power cycle is **hardware-validation pending** and must not claim saved persistence until the physical checklist proves it.

If physical testing shows that stock JM12 resets EQ/gain on power loss, the persisted app-side tracked-gain state must be made robust against stale hardware state before qualification. Do not paper over that result with a UI claim.

No verified stock-JM12 external preset-file format is exposed in v0.5. This does not remove Direct Flash.

### Shared protocol safety rules

- strict wrong-device protection;
- dynamically locate the actual HID interrupt IN/OUT interface rather than hardcoding an interface number;
- Android USB permission lifecycle must be explicit and recoverable;
- no bootloader/firmware commands;
- no reconstruction-filter, amplifier-mode, USB-mode, balance, microphone, or other unrelated DAC writes;
- unused PEQ slots are disabled/bypassed when safely supported or written to a validated flat state so stale filters cannot remain active;
- build and validate the entire target state before the first destructive write;
- stop on failed verification rather than reporting partial success.

## Reset behavior

Reset is a device action only. It never creates or modifies a canonical EQ, Favorite, General EQ, My EQs entry, or export file.

- **Black Pearl:** preserve the separately qualified v0.4 fail-safe reset behavior and tracked playback-gain restoration.
- **JA11:** return all five PEQ bands and global EQ gain to flat/0 dB, Apply, verify, Save, and verify again.
- **JM12:** return all five PEQ bands to flat and remove only EQ Library's tracked playback-gain adjustment; do not claim power-cycle persistence until hardware proves it.

## Automated validation

The v0.5 software gate requires coverage for:

- exact native representation and device quantization;
- native hardware rounding without unnecessary response fitting;
- deterministic complete-response fitting for over-budget/unrepresentable profiles;
- Peak / Low Shelf / High Shelf response evaluation;
- target-derived generated headroom without canonical mutation and never labeled Exact;
- quality gates and Not-suitable cases;
- Black Pearl pyBlackPearl `PK / LS / HS` file syntax and file/Flash plan parity;
- Black Pearl true-preamp export with importer-side range warning and no app-side clamp;
- TOPPING Tune standard AutoEq syntax, 10-band complete-response fitting, no source-preamp clamp, and conservative precision-pending fidelity;
- JA11/JM12 remain fileless while Direct Flash stays intact;
- protocol packet/register golden vectors;
- signed values, frequency, gain, Q, type, status, and byte-preservation handling;
- complete slot overwrite/flat padding;
- read/apply/save/readback ordering where supported;
- staged failure behavior;
- wrong-device and USB permission/disconnect behavior;
- Direct Flash OFF defaults;
- Reset-to-flat behavior;
- output-registry grouping/file-vs-hardware semantics;
- versioned derived-representation fingerprints/currentness.

Never weaken validation merely to turn CI green; update obsolete tests only when they conflict with an approved superseding product rule.

## Physical qualification gates

Use separate Pixel 9 hands-on records:

- `docs/FIIO_JA11_HANDS_ON_CHECKLIST.md`
- `docs/JCALLY_JM12_HANDS_ON_CHECKLIST.md`

Each physical qualification must record the exact candidate SHA, signed APK identity/hash, device/firmware identity where available, USB identity, permission/connection behavior, confirmation-cancel/no-write behavior, Exact and Optimized Flash, shelf/peak behavior, playback/global gain, complete unused-slot handling, readback, power-cycle behavior, Reset, recovery, and unchanged unrelated settings.

The v0.5 candidate must also run the focused Black Pearl regression smoke required by the shared-adapter change.

Until a device checklist passes, that device remains **Hardware validation pending** and must not be described as physically qualified.

For **v0.5.0**, JA11 and stock JM12 physical qualification are explicitly **deferred to the next incremental release** because the devices are not yet available. These two pending gates do **not** block v0.5.0 publication. Their checklists remain authoritative qualification procedures, but before they are executed the candidate identity must be refreshed to the exact signed candidate for the incremental release being tested.

## Release

Target milestone: **v0.5.0**.

A public v0.5.0 release may claim Direct Flash qualification only for hardware that has passed the exact-candidate software/signing gates and its physical gate. JA11 and JM12 may ship as implemented outputs with **Hardware validation pending** status; their deferred physical qualification is not a v0.5.0 blocker. Release copy and in-app status must state that accurately, and stock JM12 persistence must remain unclaimed.

Any behavior-affecting change after the old `c47c0f6d...` software candidate means that candidate is obsolete. Produce a new exact signed candidate after all v0.5 output/import/fidelity changes and current-main reconciliation are complete, then run any hardware gate that is actually being used to support a qualification claim against that exact APK.
