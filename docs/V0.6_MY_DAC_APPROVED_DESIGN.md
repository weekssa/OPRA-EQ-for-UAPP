# EQ Library v0.6.0 — Approved My DAC UX

Status: **Approved 2026-09-09**. This document is the v0.6 user-facing authority for My DAC. It supplements `docs/CHATGPT_PROJECT_RUNBOOK.md`, `docs/ARCHITECTURE.md`, the v0.5 hardware plans/protocol notes, and the device hands-on records. Where older hardware UX wording conflicts with this approved design, this document controls for v0.6.

## Product goal

v0.6 adds a capability-driven **My DAC** experience so a supported connected DAC can be inspected, EQ-managed, and—only where independently verified—controlled without relying on a separate vendor management app for normal supported functions.

The feature must preserve EQ Library's source-agnostic canonical EQ architecture and all qualified v0.5 behavior. It must never invent device commands, ranges, readback semantics, persistence, source attribution, or current hardware state.

Initial hardware targets remain:

- TRN Black Pearl — physically qualified EQ path; v0.6 proving device for additional controls.
- FiiO JA11 — software implemented Direct Flash; physical validation pending.
- stock-firmware JCALLY JM12 — software implemented Direct Flash; physical validation pending and persistence unclaimed.

## Navigation and USB attach

When no supported DAC has been recognized in the current app session, top-level navigation remains:

`My EQs | EQ Library | Settings`

After a supported DAC is recognized:

`My EQs | My DAC | EQ Library | Settings`

`My DAC` sits immediately beside `My EQs`.

Once `My DAC` appears in the current app session it remains present after disconnect so bottom navigation does not jump. The destination shows **Disconnected** and any retained values are explicitly labeled **Last read**, never current. A later cold app launch with no supported DAC may return to the normal three destinations.

When EQ Library is already open and a supported DAC is recognized, show a concise nonblocking `Open My DAC` prompt. Do not steal focus from an unfinished workflow.

If Android launches EQ Library from supported USB attach, route to My DAC only after normal Android device/default-app/USB-permission behavior. Never bypass or misrepresent USB permission.

## My DAC shell

My DAC uses two tabs:

- **EQ**
- **DEVICE**

The header shows device identity plus a textual connection state. Color may supplement but never replace connection/status text.

## EQ tab — hardware truth first

The EQ tab begins from an actual hardware read. It must not display assumed or cached values as current.

Required states:

### Flat

The verified hardware EQ response is flat according to the device's supported EQ semantics. Ordinary playback/global volume is separate; a DAC may correctly be `EQ: Flat` while playback gain is attenuated.

### Exact saved match

The current native hardware representation exactly equals a deterministic saved My EQs representation. Show headphone, creator/source/details, target fidelity/adaptation, filter count, slot where applicable, and relevant EQ headroom/gain context.

### Modified known EQ

Use only when lineage is defensible—for example, EQ Library previously flashed a known saved representation and later reads explicit parameter differences. Do not infer Modified from curve similarity alone.

### Unknown EQ

The hardware EQ was successfully read but cannot be truthfully associated with a saved EQ. Never guess OPRA, AutoEq, creator, headphone, or other source metadata.

## Visual EQ component

The EQ tab includes a compact parametric response visualization and the editor includes a larger version.

The graph:

- renders the combined device-native PEQ response over a log-frequency axis;
- includes a subtle 0 dB reference;
- shows active band markers;
- uses minimal frequency labels;
- may select a band by tapping its marker;
- **does not use freeform graph dragging/swiping to edit in v0.6**.

The compact graph is primarily read/select. The larger editor graph emphasizes the selected band's marker while other markers visually recede. The selected band's type/frequency/gain/Q summary appears immediately below.

Accessibility never depends on the graph: all values remain available through semantic text rows and the All Bands view.

## Edit EQ

The normal EQ screen remains status-first. **Edit EQ** opens a dedicated editor after a fresh hardware read.

Editing flow:

`Read hardware -> local working copy -> edit -> recalculate response/headroom -> validate device limits -> Review changes -> explicit Apply -> readback -> verified hardware state`

Entering or using the editor must not itself write to hardware.

### Focused band editor

A selected band exposes deliberate controls for supported properties such as:

- enabled state where the device supports it;
- filter type;
- frequency;
- gain;
- Q.

Sliders/steppers may provide quick adjustment, but tapping the displayed numeric value provides exact entry. The UI reflects actual representable device range/resolution rather than invented precision.

An **All Bands** view provides a compact table/list for advanced users instead of showing dozens of simultaneous sliders.

## Headroom and gain safety

Headroom/clipping logic is integral to the editor and uses the same deterministic response logic that protects hardware derivation.

For every local edit:

1. evaluate the actual combined quantized/planned EQ response;
2. determine the conservative required attenuation/headroom;
3. compare that requirement with the planned verified device control semantics;
4. show the result before any hardware write.

Required presentation states include:

- **Safe** — planned gain/headroom is sufficient;
- **Adjustment required** — the EQ is valid but additional safe attenuation is recommended;
- **Device limitation** — the device cannot represent enough verified attenuation or another hard capability prevents a safe result.

A `Use safe gain` action may update the **local plan**. It must never silently write hardware.

Headroom warnings are separate from filter/range warnings. A value can be inside device range yet require additional headroom, outside a conservative validated range while still wire-encodable, or completely unsupported. Do not conflate those cases.

Device semantics matter: a dedicated EQ preamp may be treated as EQ headroom when independently verified. Ordinary playback/global volume must not automatically be relabeled source preamp. Existing Black Pearl tracked EQ Library attenuation replacement and fail-safe Reset ordering remain protected.

## Review and Apply

Review changes combines filter changes and gain/headroom consequences. The user sees what will change before the first write.

Hardware writes must:

1. start from a fresh/validated state as required by that device;
2. validate the complete intended transaction before destructive writes;
3. write only required owned values while preserving unrelated bytes/settings;
4. use safe device-specific ordering;
5. read back where supported;
6. display the actual verified hardware state;
7. fail visibly on permission loss, disconnect, partial transfer, stale state, or mismatch.

A readback mismatch must never be presented as success. If the hardware returns a different value, the UI adopts and clearly labels the actual hardware state.

## Save DAC EQ

Unknown or intentionally modified hardware EQ may be captured as a local **Personal EQ** with provenance such as `Captured from TRN Black Pearl` and the actual device-native snapshot retained locally.

Association options:

- choose from My EQs;
- browse saved headphones;
- search EQ Library manufacturer/model;
- **leave unassociated**.

Do not force or invent a headphone/source association. If the hardware state already exactly matches a saved EQ, link to that EQ instead of creating a duplicate.

Editing a sourced profile preserves lineage but not false authorship. After modification, the result is a Personal EQ that may say `Based on <source/creator>`; it must not claim the original creator authored the modified values.

## Change EQ and Reset

**Change EQ** opens a device-aware My EQs chooser showing Exact/Optimized/Not-suitable state and the concise adaptation reason before the existing safe Flash review.

**Reset EQ to flat** remains a secondary explicit action and requires confirmation. Reset modifies device EQ state only; it does not create/delete canonical EQs or local membership. Preserve qualified device-specific safe ordering.

## DEVICE tab

The Device tab is capability-driven. Unsupported sections disappear instead of showing placeholders.

Potential sections, only when independently verified for that exact device, include:

- Playback
- DAC / Filter
- Output
- Microphone / Input
- USB / System
- Advanced (collapsed by default)
- Device information

Normal settings should use simple rows, bottom sheets for discrete choices, and exact numeric entry plus slider/stepper where appropriate. Avoid a wall of cards or knob-heavy UI.

Level-sensitive controls such as playback volume, gain mode, or analog PGA require special handling: read current hardware first, never reconnect by pushing cached UI state, preview slider changes locally, commit deliberately, verify readback, and avoid hidden combinations that can produce a dangerous volume jump.

## Per-device v0.6 exposure policy

### TRN Black Pearl

Existing qualified EQ/slot/playback-gain behavior remains. Additional v0.6 candidate controls—digital filter, gain mode, amp topology, balance, mic gain, firmware readback—must pass EQ Library's own read/write/readback qualification on the physical Black Pearl before normal production exposure.

### FiiO JA11

Keep existing five-band EQ/global-EQ-gain Direct Flash semantics. DAC digital filter is a strong candidate but remains hardware-validation pending. Playback volume and microphone controls remain hidden until their exact commands/ranges/readback semantics are independently established.

### stock JCALLY JM12

Keep existing five-band DAC EQ/enable/digital-gain behavior. Broader KT02H20 register-map controls remain hidden until proven appropriate and safe on the exact stock JM12. Never expose writes to USB manufacturer/product/serial/VID/PID. Do not claim persistence across power cycle until physically qualified.

## Device information

Clearly distinguish origins:

- **Reported by USB** — e.g. VID/PID or USB strings;
- **Reported by device** — e.g. firmware if actually read;
- **Known device capability** — static qualified/corroborated model knowledge;
- **EQ Library validation status** — qualified or hardware validation pending.

Never display static/inferred metadata as though the connected device reported it.

## Permission, loading, disconnect and error states

### Permission required

Explain that Android USB permission is required to read/manage the DAC. Do not show guessed current settings.

### Loading

Use read-first wording such as `Reading device information`, `Reading EQ`, and `Reading supported controls`, with explicit `No settings are being changed` where useful.

### Disconnected

Keep the My DAC destination for the current session and label retained data `Last read`. Never present stale controls as current.

### Disconnect during local editing

Keep unsent edits available, but re-read hardware on reconnect. If hardware changed externally, require reconciliation before Apply.

### Disconnect/permission loss during write

Do not assume completion. Reconnect/recover read-only first, then present actual hardware state.

## Visual and accessibility baseline

Pixel 9 baseline:

- approximately 20–24dp horizontal padding;
- 48dp minimum interactive targets;
- compact main EQ graph about 150–170dp;
- editor graph about 210–240dp;
- simple rows/dividers with generous vertical spacing;
- one dominant primary action per major state;
- light/dark modes equally intentional;
- 150–220ms subtle selection/state transitions and Android reduced-motion respect.

TalkBack announces control name/value/range and write verification state. Numeric editing supplements sliders. Large fonts reflow rather than clip. Status is never color-only.

## Explicitly out of scope for v0.6 normal My DAC controls

- firmware flashing / bootloader / cross-flash;
- identity mutation (VID/PID, USB strings);
- speculative chipset-similar controls;
- arbitrary raw register/command consoles;
- freeform graph drag-to-write;
- silent gain/filter clamping;
- automatic cached-state restoration to hardware;
- false source attribution;
- unqualified persistence claims.
