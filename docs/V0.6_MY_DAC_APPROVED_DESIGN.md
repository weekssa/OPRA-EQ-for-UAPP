# EQ Library v0.6.0 — Approved My DAC UX

Status: **Approved 2026-09-09; expanded Black Pearl/FiiO direction approved 2026-09-13**. This document is the v0.6 user-facing authority for My DAC. It supplements `docs/CHATGPT_PROJECT_RUNBOOK.md`, `docs/ARCHITECTURE.md`, the v0.5 hardware plans/protocol notes, and the device hands-on records. Later explicit product decisions in this document supersede older hardware wording.

## Product goal

v0.6 adds a capability-driven **My DAC** experience so a supported connected DAC can be inspected, EQ-managed, and—only where independently established and appropriately qualified—controlled without relying on a separate vendor management app for normal supported functions.

The feature must preserve EQ Library's source-agnostic canonical EQ architecture and all qualified behavior. It must never invent device commands, ranges, readback semantics, persistence, source attribution, or current hardware state.

Current device roadmap:

**TRN Black Pearl → FiiO**

- TRN Black Pearl — active development and physical qualification reference hardware.
- FiiO/JadeAudio JA11 — full software buildout proceeds before hardware arrival; physical validation remains pending.
- JCALLY — not part of the current, upcoming, experimental, or pending product UX. Historical/internal research may remain, but connected JCALLY hardware follows normal unsupported-device behavior.

## Automatic output behavior

The default is **Automatic (recommended)**.

The user should not have to preselect a supported DAC before plugging it in. When exactly one current supported DAC is physically present, Automatic makes that DAC the effective output context for My EQs/EQ Library derivation and hardware actions. The DAC does not need to have been pre-enabled in the output list.

When no supported DAC is present, Automatic falls back to the user's saved normal/manual output. When more than one supported DAC is present, EQ Library must not guess; retain the saved fallback and let My DAC present an explicit device chooser.

Settings provides a persistent **Manual** override. Selecting a manual output keeps that choice until the user restores Automatic.

My DAC itself always represents actual connected hardware. Output behavior must never fabricate a physical connection.

## Navigation and USB attach

When no supported DAC has been recognized in the current app session, top-level navigation remains:

`My EQs | EQ Library | Settings`

After a supported DAC is recognized:

`My EQs | My DAC | EQ Library | Settings`

`My DAC` sits immediately beside `My EQs`.

Once `My DAC` appears in the current app session it remains present after disconnect so bottom navigation does not jump. The destination shows **Disconnected** and any retained values are explicitly labeled **Last read**, never current. A later cold app launch with no supported DAC may return to the normal three destinations.

When EQ Library is already open and a supported DAC is recognized, show a concise nonblocking `Open My DAC` prompt. Do not steal focus from an unfinished workflow.

If Android launches EQ Library from supported USB attach, route to My DAC only after normal Android device/default-app/USB-permission behavior. Never bypass or misrepresent USB permission.

A supported DAC should be recognized from its exact maintained USB identity without requiring prior output selection. If Android already retains permission, reconnect may reopen the session automatically; if permission is required, use the normal Android permission flow.

## My DAC shell

My DAC uses two tabs:

- **EQ**
- **DEVICE**

The header shows device identity plus a textual connection state. Color may supplement but never replace connection/status text.

Keep navigation simple: **My EQs** is what the user owns/uses, **My DAC** is actual connected hardware, **EQ Library** is discovery, and **Settings** is preferences/overrides. Do not add per-vendor top-level destinations.

## EQ tab — hardware truth first

The EQ tab begins from an actual hardware read. It must not display assumed or cached values as current.

Required states:

### Flat

The verified hardware EQ response is flat according to the device's supported EQ semantics. Ordinary playback/global volume is separate; a DAC may correctly be `EQ: Flat` while playback level is attenuated.

### Exact saved match

The current native hardware representation exactly equals a deterministic saved My EQs representation. Show headphone, creator/source/details, target fidelity/adaptation, filter count, slot where applicable, and relevant EQ headroom/gain context.

### Modified known EQ

Use only when lineage is defensible—for example, EQ Library previously flashed a known saved representation and later reads explicit parameter differences. Do not infer Modified from curve similarity alone.

### Unknown EQ

The hardware EQ was successfully read but cannot be truthfully associated with a saved EQ. Never guess OPRA, AutoEq, creator, headphone, or other source metadata.

### Device-built-in EQ state

When a DAC exposes built-in EQ programs separately from a user PEQ bank, read the active program first. Do not display stored user-PEQ coefficients as current if a built-in preset is active. If the built-in preset's actual coefficients are not readable, identify the verified program name without inventing a response curve.

## Visual EQ component

The EQ tab includes a compact parametric response visualization and the editor includes a larger version.

The graph:

- renders the combined device-native PEQ response over a log-frequency axis;
- includes a subtle 0 dB reference;
- shows active band markers;
- uses minimal frequency labels;
- may select a band by tapping its marker;
- **does not use freeform graph dragging/swiping to edit in v0.6**.

Accessibility never depends on the graph: all values remain available through semantic text rows and the All Bands view.

## Edit EQ

The normal EQ screen remains status-first. **Edit EQ** opens a dedicated editor after a fresh hardware read.

Editing flow:

`Read hardware -> local working copy -> edit -> recalculate response/headroom -> validate device limits -> Review changes -> explicit Apply -> readback -> verified hardware state`

Entering or using the editor must not itself write to hardware.

A selected band exposes deliberate supported controls for enabled state where applicable, filter type, frequency, gain, and Q. Sliders/steppers may provide quick adjustment, but tapping the displayed numeric value provides exact entry. The UI reflects actual representable device range/resolution rather than invented precision.

An **All Bands** view provides a compact table/list for advanced users instead of showing dozens of simultaneous sliders.

## Headroom and gain safety

Headroom/clipping logic is integral to the editor and uses the same deterministic response logic that protects hardware derivation.

For every local edit:

1. evaluate the actual combined quantized/planned EQ response;
2. determine the conservative required attenuation/headroom;
3. compare that requirement with the planned verified device control semantics;
4. show the result before any hardware write.

Required presentation states include **Safe**, **Adjustment required**, and **Device limitation**. `Use safe gain` may update the local plan but must never silently write hardware.

Headroom warnings are separate from filter/range warnings. A value can be inside device range yet require additional headroom, outside a conservative validated range while still wire-encodable, or completely unsupported.

Device semantics matter. A dedicated EQ preamp may be treated as EQ headroom when independently verified. Ordinary playback volume must not automatically be relabeled source preamp.

## Review and Apply

Review changes combines filter changes and gain/headroom consequences. The user sees what will change before the first write.

Hardware writes must:

1. start from fresh/validated actual state;
2. validate the complete intended transaction before destructive writes;
3. write only required owned values while preserving unrelated settings;
4. use safe device-specific ordering;
5. read back where supported;
6. display only actual verified hardware state as current;
7. fail visibly on permission loss, disconnect, partial transfer, stale state, or mismatch.

A readback mismatch must never be presented as success. USB session replacement invalidates an ordinary same-session write and must never trigger a silent retry.

For controls whose intended behavior itself re-enumerates/restarts USB, transfer completion is only an intermediate state. Success requires a replacement session plus fresh read verifying the requested value.

## Save DAC EQ

Unknown or intentionally modified hardware EQ may be captured as a local **Personal EQ** with actual device-native values and provenance such as `Captured from TRN Black Pearl` or `Captured from FiiO JA11`.

Association options include My EQs, saved/library headphone, search, or intentionally unassociated. Do not force or invent a source association. Exact existing matches link instead of duplicating.

Editing a sourced profile preserves lineage but not false authorship. After modification, the result is a Personal EQ that may say `Based on <source/creator>`; it must not claim the original creator authored the modified values.

## Change EQ and Reset

**Change EQ** opens a device-aware My EQs chooser showing Exact/Optimized/Not-suitable state and concise adaptation reason before the existing safe Flash review.

**Reset EQ to flat** remains a secondary explicit action and requires confirmation. Reset modifies device EQ state only; it does not create/delete canonical EQs or local membership. Preserve device-specific ordering and verification.

## DEVICE tab

The DEVICE tab is capability-driven. Unsupported controls disappear instead of showing placeholders.

Use grouped progressive disclosure rather than adding navigation destinations:

1. compact overview / most-used current values;
2. **Playback**;
3. **DAC / Digital**;
4. **Output**;
5. **Microphone / Input**;
6. **USB / System**;
7. **Advanced** (collapsed by default);
8. **Device information**.

The first screenful should prioritize connection, volume where supported, current EQ, and common settings. Rare or disruptive controls belong lower in the hierarchy or under Advanced.

Normal settings use simple rows, bottom sheets for discrete choices, and exact numeric entry plus slider/stepper where appropriate. Avoid a wall of cards or knob-heavy UI.

Provide one obvious **Refresh device state** action. Current/stale state is communicated at section/screen level rather than by duplicating noisy labels on every row.

Level-sensitive controls such as playback volume or hardware gain require special handling: read hardware first, never reconnect by pushing cached state, preview changes locally, commit deliberately, verify readback, and prevent stale-state volume jumps.

## Per-device v0.6 exposure policy

### TRN Black Pearl

Black Pearl is the active physical qualification reference. Existing qualified EQ/slot/reset behavior remains protected.

Software may implement the full normal-control framework for reconstruction filter, gain mode, amp topology, balance, mic gain, and playback/global level. Each new write graduates independently through maintained physical qualification. Passing read-only qualification does not itself qualify writes.

### FiiO / JadeAudio JA11

JA11 is the next full software target. Build as much normal functionality as independently established before hardware arrives, then perform physical validation/tweaks on one consolidated candidate.

Current software-established/corroborated normal surface includes:

- exact JA11 identity in both UAC modes (`2972:0101` UAC 1.0 and `2972:0102` UAC 2.0);
- five-band User 1 PEQ and dedicated PEQ master gain;
- active EQ program: Vocal / Classic / Bass / User 1 / Off;
- independent output volume `0..60` as native device units;
- headset microphone / inline remote control;
- UAC 1.0 / UAC 2.0 selection;
- current stream/sample-rate readback;
- firmware readback;
- existing Apply/Save/Reset PEQ behavior.

JA11 writes remain **Hardware validation pending** until the exact hardware checklist passes. Level-sensitive and session-disruptive controls receive stricter review/readback behavior.

No JA11 SPDIF control has been established. Do not invent one. The generic FiiO architecture should support a future Digital Output/SPDIF capability on exact future models when independently verified.

### Future FiiO models

Reuse generic device/capability/session/UI infrastructure, but never project JA11 commands or capabilities onto another model. Auto-identify only exact maintained identities. Potential per-model modules may include volume, gain, filters, output mode, SPDIF/DoP/D2P, microphone/input, UAC/USB, EQ programs, and device information only when that exact model establishes them.

### JCALLY

JCALLY is absent from current product UX/support. No supported-device card, selector, pending state, roadmap row, hidden fallback write path, or user-facing JCALLY-specific feature may remain. Useful historical protocol/safety research and generic shared infrastructure may remain internally.

## Device information

Clearly distinguish origins:

- **Reported by USB** — e.g. actual VID/PID or USB strings;
- **Reported by device** — e.g. firmware if actually read;
- **Known device capability** — static corroborated/qualified model knowledge;
- **EQ Library validation status** — hardware-qualified or hardware-validation-pending.

Never display static/inferred metadata as though the device reported it.

## Permission, loading, disconnect and error states

### Permission required

Explain that Android USB permission is required to read/manage the DAC. Do not show guessed current settings.

### Loading

Use read-first wording such as `Reading device information`, `Reading EQ`, and `Reading supported controls`, with explicit `No settings are being changed` where useful.

### Disconnected

Keep My DAC destination for the current session and label retained data `Last read`. Never present stale controls as current.

### Disconnect during local editing

Keep unsent edits available, but re-read hardware on reconnect. If hardware changed externally, require reconciliation before Apply.

### Disconnect/permission loss during write

Do not assume completion. Reconnect/recover read-only first, then present actual hardware state.

## Visual and accessibility baseline

Pixel 9 baseline:

- approximately 20–24dp horizontal padding;
- 48dp minimum interactive targets;
- compact main EQ graph about 150–170dp;
- editor graph about 210–240dp;
- simple rows/dividers with generous vertical spacing;
- one dominant primary action per major state;
- light/dark modes equally intentional;
- TOPPING-reference product blue `#257BFF`, with contrast-safe variants where required;
- semantic error/warning/success/disabled colors remain semantic rather than mechanically recolored;
- 150–220ms subtle selection/state transitions and Android reduced-motion respect.

TalkBack announces control name/value/range and write verification state. Numeric editing supplements sliders. Large fonts reflow rather than clip. Status is never color-only.

## Explicitly out of scope for v0.6 normal My DAC controls

- firmware flashing / bootloader / cross-flash;
- identity mutation (VID/PID, USB strings);
- speculative chipset-similar controls;
- arbitrary raw register/command consoles;
- freeform graph drag-to-write;
- silent gain/filter clamping;
- automatic cached-state restoration to hardware;
- false source attribution;
- unqualified persistence claims;
- JA11 SPDIF or reconstruction-filter controls without independent evidence.

## Software-first / physical-test gate

The owner explicitly requested that FiiO/Black Pearl software work and automated regression testing be driven as far as safely possible before requesting hands-on testing. Do not interrupt the development cycle for incremental FiiO physical checks while independent software work remains.

When software-side work is exhausted, pin one exact signed candidate and begin physical qualification **one small safe test at a time** with direct APK provenance.
