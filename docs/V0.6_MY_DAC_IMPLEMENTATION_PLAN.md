The approved My DAC core is implemented on `v0.6-my-dac`, including conditional/session-sticky navigation, actual Black Pearl hardware EQ readback and deterministic matching, response graphs, fresh-read local editing with headroom planning, Review → Apply → verified readback, Save DAC EQ, and the qualified DEVICE read/write framework.

- keep USB audio mode read-only, with a brief manual Black Pearl UAC startup sequence under the row;
- no generic Save-device-settings or Restore-defaults action unless exact device semantics establish one.

The existing hardware transaction safety remains authoritative under the simpler UI. No protocol validation is weakened to make the screen feel immediate.

Subsequent UX-only refactoring does not retroactively change those physical observations; any changed hardware transaction behavior requires a new focused qualification.

## Goals

v0.6 adds a native, capability-driven connected-DAC experience while preserving the source-agnostic canonical library and all qualified v0.5 hardware behavior.

The implementation must:

- keep canonical/source data independent from device state;
- make actual connected hardware state readable without guessing;
- match actual native hardware EQ against deterministic My EQs representations;
- support Flat / Exact match / Modified-known / Unknown states;
- support deliberate manual EQ editing with visual response preview and live headroom validation;
- support safe Review -> Apply -> readback verification for multi-band manual EQ editing;
- capture unknown/modified DAC EQ as a local Personal EQ without false attribution;
- expose only independently verified device controls;
- preserve USB permission/lifecycle safety across configuration changes;
- preserve v0.5 Direct Flash and Reset behavior during refactoring;
- minimize user-visible duplication and qualification-oriented prose.

Target release: **v0.6.0**.

## Evidence policy

Each control is classified as one of:

1. **Qualified** — exact hardware path has passed EQ Library physical validation.
2. **Software established / hardware pending** — protocol/semantics are strong enough for clean-room implementation and automated tests, but the exact physical gate has not passed.
3. **Corroborated candidate** — credible external evidence exists, but exact semantics/range/persistence/safety are incomplete; design may anticipate it, production exposure remains hidden.
4. **Hidden/prohibited** — insufficiently established or unnecessarily risky.

Every candidate control audit records command/register, read/write direction, range/units, quantization, owned bits/bytes, persistence, readback, failure behavior, evidence, physical-validation state, and safety class.

Observable facts from public reference implementations may corroborate behavior, but incompatible code must not be copied. Device behavior is implemented clean-room from independently established protocol facts and EQ Library's own tests.

## Architecture target

### Session ownership

`DacSessionRepository` is the sole ViewModel-scoped owner/coordinator of a physical supported-DAC session. Configuration changes must not replace a live session. The session closes when the ViewModel is actually cleared.

`HardwareEqRepository` remains about deterministic hardware EQ actions, not general device-management controls. Existing Flash/Reset semantics remain protected behind the shared session abstraction.

`DacControlRepository` exposes typed, capability-driven read/write operations. Compose never branches on protocol constants, VID/PID, report IDs, register addresses, or raw bytes.

### App-wide connection/read contract

A successful supported-DAC connection triggers the app's authoritative fresh read of both hardware EQ and supported DEVICE controls. My EQs, My DAC and EQ Library consume that same session state.

Successful hardware mutations refresh state automatically:

- Direct Flash -> refresh EQ and relevant playback/device state;
- Reset -> refresh EQ and relevant playback/device state;
- manual editor Apply -> refresh EQ and relevant device state;
- DEVICE control write -> refresh DEVICE state and any semantically affected summary state.

The manual Refresh action is retained only for external changes or recovery, not as a required step after navigating or saving.

## Domain model

Framework-independent `domain/dac` types cover:

- device identity and validation status;
- session/connection state;
- immutable capability set;
- typed control descriptors;
- typed control values;
- state freshness/origin;
- verified write results;
- native EQ snapshot;
- EQ match result;
- local edit working state and headroom assessment.

The domain layer must not depend on Android `Context`, USB classes, Compose, Room, or device-specific transports.

## EQ response/headroom domain

Manual editing reuses deterministic response evaluation principles rather than inventing a UI-only heuristic.

For an editable native plan:

1. validate every filter against target-supported semantics;
2. quantize/normalize only at the device boundary according to the exact target contract;
3. evaluate the combined response on the shared deterministic frequency grid;
4. derive conservative required headroom from the final planned response;
5. compare required headroom to the verified device gain/preamp mechanism that actually protects the path;
6. classify Safe / AdjustmentRequired / DeviceLimited;
7. keep this calculation in domain code and cover it with deterministic unit tests.

Do not silently modify filter values or hardware gain. `Use safe gain` updates only the local working plan until the explicit editor Apply transaction.

## Snapshot + deterministic match

Each supported device adapter reads actual native EQ state and converts it to a framework-independent `HardwareEqSnapshot` without claiming source attribution.

Matching rules:

- Flat only when the native EQ semantics are flat;
- Exact only on deterministic native equality with a saved derived representation;
- ModifiedKnown only when lineage is explicitly known and differences are exact;
- otherwise Unknown.

Cold-start similarity never establishes provenance.

The My DAC destination does not ask a second time to connect when the shared supported-DAC session is already connected.

Implement:

- Flat / Exact / Modified / Unknown screens;
- compact combined-response graph;
- active band markers;
- text alternatives and TalkBack semantics;
- concise technical details;
- Save DAC EQ / Edit EQ / Reset actions according to state.

The graph is read/select only in v0.6. It must not drag-write.

The former My DAC **Change EQ** chooser is removed. My EQs and EQ Library own EQ choice/Flash; My DAC owns current hardware truth, editing/capture/reset.

## Direct Flash surfaces

My EQs retains its existing Flash action for compatible saved EQs.

EQ Library exposes the same safe Direct Flash path from the normal library/profile surface whenever the physically connected supported DAC and deterministic output representation permit it. The action must not require first adding the EQ to My EQs merely to flash it.

Flash confirmation is concise and built from the same actual plan used by the transaction: EQ identity, Exact/Optimized state, concise adaptation reason, filter count, required playback adjustment, and genuine caution only. Advanced source metadata remains available on the EQ detail surface and is not repeated inside a modal wall of text.

## Manual EQ editing

Manual EQ editing remains a staged expert operation:

- fresh-read entry into editor;
- local immutable/controlled working copy;
- tap-to-select graph markers;
- focused band editor;
- exact numeric entry;
- All Bands view;
- live domain headroom assessment;
- separate device-limit and unsupported-value warnings;
- Review changes screen;
- no device write until explicit Apply.

This is intentionally different from routine DEVICE controls because it can change the entire PEQ plan and headroom together.

## Apply + verified readback

Use a typed transaction plan per device.

Rules:

- validate entire target before first destructive write;
- preserve unrelated bytes/settings;
- use existing qualified gain-delta replacement rules where applicable;
- use safe ordering for level-affecting values;
- verify final filters and relevant gain/preamp state;
- surface readback mismatch explicitly;
- recover read-first after disconnect/permission loss/partial transfer;
- never report requested local state as current until verification succeeds.

Black Pearl v0.5 qualified Flash/Reset behavior is the baseline regression contract.

## Save DAC EQ

Persist captured hardware state as Personal EQ with:

- actual native values;
- capture device/model identity;
- capture timestamp/session metadata;
- `Captured from <DAC>` provenance;
- no invented source creator;
- optional headphone association;
- unassociated state permitted.

If exact match already exists, link instead of duplicate.

## Generic DEVICE controls

Implement only controls that clear the evidence/qualification gate for that exact model.

Typed control pipeline remains:

`fresh validated baseline -> user choice -> validate -> write owned value -> readback -> Verified/Failure -> refresh current state`

The UI presentation is simpler than the transaction. Routine controls should not show the transaction algorithm to the user.

### Interaction policy

- **Normal** controls — choose a value and apply immediately, with a short applying/verified/error state.
- **LevelSensitive** controls — choose/adjust deliberately; show a short plain-language confirmation only when the change may produce a material level jump.
- **Destructive** controls — remain explicit confirmed actions. EQ Reset remains its separately approved flow.

No normal DEVICE write silently retries after transfer. Same-session bounded settling reads remain acceptable where already qualified because they re-read without resending the write.

No global Save-to-flash action is added unless a separate verified persistence operation is genuinely required.

## Black Pearl USB audio mode

The current UAC 1.0/2.0 mode is read from the replacement session's standard USB AudioControl descriptors. It remains read-only because no exact Black Pearl software UAC command is established.

User-facing help is concise:

- UAC 1.0: disconnect the Black Pearl, keep headphones connected, hold `+` and `−`, reconnect USB, release after power/enumeration;
- UAC 2.0: reconnect normally without holding the buttons;
- EQ Library automatically re-reads the new session and displays the detected mode.

The app never claims that a generic vendor command switches modes.

## Physical qualification preservation

Completed Black Pearl qualification evidence remains attached to the exact behavior candidates on which it was observed. A Compose/navigation/string refactor does not invalidate protocol qualification when the underlying transaction is unchanged.

If this UX work changes connection ownership, read timing, write sequencing, write values, verification rules, persistence calls, or session generation behavior, pin a new signed candidate and perform the smallest focused hardware regression needed for the changed behavior.

## Software-first / physical-test gate

Continue software implementation and automated regression as far as safely possible before requesting hands-on testing. When software-side work is exhausted, pin one exact signed candidate and request only the focused physical checks that are genuinely necessary for behavior changed since the last qualified candidate.
