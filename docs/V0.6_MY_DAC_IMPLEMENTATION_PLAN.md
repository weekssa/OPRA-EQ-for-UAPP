# EQ Library v0.6.0 — My DAC implementation plan

Status: **Approved UX; implementation in progress**.

This is the v0.6 implementation authority for My DAC. Read it with `docs/CHATGPT_PROJECT_RUNBOOK.md`, `docs/ARCHITECTURE.md`, `docs/V0.6_MY_DAC_APPROVED_DESIGN.md`, the v0.5 hardware plan, and the applicable device protocol/hands-on notes.

## Goals

v0.6 adds a native, capability-driven connected-DAC experience while preserving the source-agnostic canonical library and all qualified v0.5 hardware behavior.

The implementation must:

- keep canonical/source data independent from device state;
- make actual connected hardware state readable without guessing;
- match actual native hardware EQ against deterministic My EQs representations;
- support Flat / Exact match / Modified-known / Unknown states;
- support deliberate manual EQ editing with visual response preview and live headroom validation;
- support safe Review -> Apply -> readback verification;
- capture unknown/modified DAC EQ as a local Personal EQ without false attribution;
- expose only independently verified device controls;
- preserve USB permission/lifecycle safety across configuration changes;
- preserve v0.5 Direct Flash and Reset behavior during refactoring.

Target release: **v0.6.0**.

## Evidence policy

Each control is classified as one of:

1. **Qualified** — exact hardware path has passed EQ Library physical validation.
2. **Software established / hardware pending** — protocol/semantics are strong enough for clean-room implementation and automated tests, but the exact physical gate has not passed.
3. **Corroborated candidate** — credible external evidence exists, but exact semantics/range/persistence/safety are incomplete; design may anticipate it, production exposure remains hidden.
4. **Hidden/prohibited** — insufficiently established or unnecessarily risky.

Every candidate control audit records command/register, read/write direction, range/units, quantization, owned bits/bytes, persistence, readback, failure behavior, evidence, physical-validation state, and safety class.

Observable facts from public reference implementations may corroborate behavior, but incompatible code must not be copied. Device behavior is implemented clean-room from independently established protocol facts and EQ Library's own tests.

## Architecture target

### Current limitation

`HardwareEqRepository` currently owns the Black Pearl, JA11, and JM12 transports directly. That was appropriate for Direct Flash-only v0.5, but a full My DAC surface would otherwise force generic device management into the EQ repository or create duplicate USB session owners.

### v0.6 ownership model

Conceptual dependency flow:

```text
MainActivity
  Android USB attach / permission / intent boundary
                    |
                    v
          EqLibraryViewModel
          immutable UI state
                    |
      +-------------+--------------+
      |                            |
      v                            v
DacSessionRepository         My EQs / Catalog
      |
      +-> DacControlRepository
      |      +-> device-specific control adapters
      |
      +-> HardwareEqRepository
             +-> existing deterministic Flash/Reset domain path
```

`DacSessionRepository` becomes the sole ViewModel-scoped owner/coordinator of a physical supported-DAC session. Configuration changes must not replace a live session. The session closes when the ViewModel is actually cleared.

`HardwareEqRepository` remains about deterministic hardware EQ actions, not general device-management controls. Existing Flash/Reset semantics remain protected while transport/session ownership is migrated behind a narrower shared session abstraction.

`DacControlRepository` exposes typed, capability-driven read/write operations. Compose never branches on protocol constants, VID/PID, report IDs, register addresses, or raw bytes.

## Domain model — first implementation increment

Add framework-independent `domain/dac` types for:

- device identity and validation status;
- session/connection state;
- immutable capability set;
- typed control descriptors;
- typed control values;
- state freshness/origin;
- verified write results;
- native EQ snapshot;
- EQ match result;
- local edit working state and headroom assessment.

The domain layer must not depend on Android `Context`, USB classes, Compose, Room, or device-specific transports.

### Suggested core types

`DacDeviceId`
- stable EQ Library target identity for supported DAC models.

`DacDeviceIdentity`
- target/model identity;
- USB VID/PID;
- USB/product strings where actually reported;
- firmware/serial fields only when actually reported;
- validation status;
- metadata-origin markers where needed.

`DacSessionState`
- NotPresent;
- PermissionRequired;
- Connecting;
- Reading;
- Connected;
- Disconnected(lastReadAt?);
- Error.

`DacCapabilities`
- supported EQ capability reference;
- ordered generic control descriptors;
- persistence semantics;
- readback availability;
- device-info fields.

`DacControlDescriptor<T>`
- stable ID;
- section;
- title/description key;
- safety class;
- read/write support;
- value contract.

Value contracts include discrete, boolean, numeric, and read-only information. Numeric contracts declare unit, minimum, maximum, step/quantization, and optional normal/caution range.

`DacControlState<T>`
- descriptor ID;
- actual value;
- freshness/origin;
- verified timestamp/session generation.

`DacWriteIntent<T>`
- control ID;
- expected baseline/session generation;
- requested target value.

`VerifiedDacWriteResult<T>`
- Verified(actual value);
- ReadbackMismatch(requested, actual);
- Disconnected;
- PermissionLost;
- StaleBaseline;
- TransferFailed.

`HardwareEqSnapshot`
- device identity;
- active slot where applicable;
- native filters;
- dedicated EQ preamp/headroom control where independently semantically valid;
- relevant playback/global gain context kept semantically distinct;
- readback/session generation.

`HardwareEqMatch`
- Flat;
- Exact(saved representation identity);
- ModifiedKnown(saved representation identity, explicit differences);
- Unknown.

Do not add fuzzy nearest-curve attribution to this model.

## EQ response/headroom domain

Manual editing must reuse deterministic response evaluation principles rather than inventing a UI-only heuristic.

For an editable native plan:

1. validate every filter against target-supported semantics;
2. quantize/normalize only at the device boundary according to the exact target contract;
3. evaluate the combined response on the shared deterministic frequency grid;
4. derive conservative required headroom from the final planned response;
5. compare required headroom to the verified device gain/preamp mechanism that actually protects the path;
6. classify Safe / AdjustmentRequired / DeviceLimited;
7. keep this calculation in domain code and cover it with deterministic unit tests.

Do not silently modify filter values or hardware gain. `Use safe gain` updates only the local working plan until the explicit Apply transaction.

## Session/discovery increment

After the framework-independent domain model is green:

- introduce a shared DAC-session contract;
- migrate existing three transports behind that contract without changing device protocol behavior;
- preserve existing ViewModel-scoped lifetime;
- keep Android USB permission/attach/detach at the platform boundary;
- make one session owner authoritative so generic controls and EQ transactions cannot compete for the same HID interface;
- add session-generation/staleness protection so cached/editing state cannot write after reconnect without a fresh read.

A migration commit must be behavior-preserving for existing Direct Flash/Reset and pass all existing hardware-domain tests before adding new device controls.

## Snapshot + deterministic match increment

Add read-only native EQ snapshots first.

For each supported device, the adapter reads the actual native EQ state and converts it to a framework-independent `HardwareEqSnapshot` without claiming source attribution.

Matching rules:

- Flat only when the native EQ semantics are flat;
- Exact only on deterministic native equality with a saved derived representation;
- ModifiedKnown only when lineage is explicitly known and differences are exact;
- otherwise Unknown.

Cold-start similarity never establishes provenance.

Add tests for:

- exact equality;
- native quantization equality;
- Flat;
- unknown arbitrary state;
- modified-known explicit difference reporting;
- source metadata never attached to Unknown.

## My DAC navigation/shell increment

Once session + snapshot logic is green, add the approved shell:

- conditional `My DAC` bottom destination after supported-device recognition;
- session-sticky destination after disconnect;
- EQ / DEVICE tabs;
- Android attach -> normal permission flow -> My DAC routing;
- already-open nonblocking Open My DAC prompt;
- permission/loading/disconnected/error states.

UI state remains one immutable `EqLibraryUiState`; `EqLibraryViewModel` orchestrates repositories and receives no `Context`.

No generic device writes are introduced in this increment.

## EQ status + visual graph increment

Implement:

- Flat / Exact / Modified / Unknown screens;
- compact combined-response graph;
- active band markers;
- text alternatives and TalkBack semantics;
- technical details;
- Change EQ / Save DAC EQ / Edit EQ / Reset actions according to state.

The graph is read/select only in v0.6. It must not drag-write.

Graph math consumes domain-provided deterministic native/planned filter values and must not become a second DSP authority.

## Manual EQ editing increment

Add:

- fresh-read entry into editor;
- local immutable/controlled working copy;
- tap-to-select graph markers;
- focused band editor;
- exact numeric entry;
- All Bands view;
- live domain headroom assessment;
- separate device-limit and unsupported-value warnings;
- Review changes screen;
- no device write until explicit Apply.

The editor must support the exact device's verified filter types/ranges only.

## Apply + verified readback increment

Use a typed transaction plan per device.

Rules:

- validate entire target before first destructive write;
- preserve unrelated bytes/settings;
- use existing qualified gain-delta replacement rules where applicable;
- use safe ordering for level-affecting values;
- verify final filters and relevant gain/preamp state;
- surface readback mismatch explicitly;
- recover read-first after disconnect/permission loss/partial transfer;
- never report requested local state as current until verification succeeds.

Black Pearl v0.5 qualified Flash/Reset behavior is the baseline regression contract.

## Save DAC EQ increment

Persist captured hardware state as Personal EQ with:

- actual native values;
- capture device/model identity;
- capture timestamp/session metadata;
- `Captured from <DAC>` provenance;
- no invented source creator;
- optional headphone association;
- unassociated state permitted.

If exact match already exists, link instead of duplicate.

Add migration/schema work only when the persistence model is fully specified and covered by Room migration tests.

## Generic Device controls increment

Implement only controls that clear the evidence/qualification gate for that exact model.

Typed control pipeline:

`fresh read -> display actual -> local user intent -> validate -> write owned value -> readback -> Verified/Failure`

Never use a similarly named control from another DAC as evidence.

### Safety classes

- **Normal** — e.g. reconstruction filter, modest balance/input controls after verification.
- **LevelSensitive** — playback volume, hardware gain, analog PGA, output stage changes capable of audible level jumps.
- **Destructive** — resets/identity changes. Identity writes are out of v0.6; EQ Reset remains its separately approved explicit action.

Level-sensitive controls never reconnect by restoring cached UI state.

## Device-specific v0.6 qualification sequence

### TRN Black Pearl

1. Read-only qualification on the user's physical Black Pearl: firmware, filter, gain mode, amp topology, balance, mic gain, playback/global gain with no writes.
2. Compare repeated reads/reconnect behavior.
3. Add protocol golden tests for candidate controls.
4. Perform one safe controlled write/readback at a time only after the read phase passes.
5. Verify persistence/reconnect behavior per control before product wording.
6. Re-run all existing Black Pearl Flash/Reset regression tests and focused Pixel 9 hardware smoke on the exact candidate.

Candidate controls must stay hidden until the relevant qualification state is achieved.

### FiiO JA11

- Existing Direct Flash remains Hardware validation pending.
- DAC reconstruction filter may be implemented behind hardware-pending gating if clean-room protocol tests are strong enough.
- Do not expose playback volume/microphone settings until exact protocol semantics are established.

### stock JCALLY JM12

- Existing Direct Flash remains Hardware validation pending.
- Broader register-map controls stay hidden until exact-device qualification.
- Never expose USB identity writes.
- Power-cycle persistence remains unclaimed until proven.

4. Read-only native EQ snapshots.

## Release gates

Do not publish v0.6.0 until:

- all intended v0.6 implementation increments are complete;
- Android unit/lint/build/current catalog/release automation gates pass;
- Black Pearl behavior affected by v0.6 has passed the exact-candidate focused hardware regression;
- any new Black Pearl Device controls exposed as normal have passed their own exact-candidate physical qualification;
- JA11/JM12 wording remains Hardware validation pending unless their exact physical gates pass;
- stock JM12 persistence remains unclaimed unless proven;
- release signing uses the established identity;
- `CHANGELOG.md` and What’s New/release notes reflect actual qualified behavior;
- the user explicitly authorizes publication.

Testing belongs to the v0.6.0 release lifecycle; it is not a separate v0.7 milestone.
