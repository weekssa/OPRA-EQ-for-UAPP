# EQ Library v0.6 — Premium UX audit blueprint

Status: **APPROVED — implementation authorized within this blueprint.**

Date: 2026-09-14

This blueprint evaluates the current v0.6 information architecture and interaction model after the shared-DAC-session and device-agnostic My EQs refactors. The project owner explicitly approved the combined direction on 2026-09-14. The existing qualified hardware/session/transaction semantics remain authoritative.

Primary user pain points this blueprint must resolve visually and behaviorally:

1. one successful DAC connection should unlock the whole app; navigation must not feel like reconnect/read ceremonies;
2. device-setting changes must not be wrapped in wordy review/save concepts when the hardware already applies/persists them;
3. EQ Flash belongs on the EQ in My EQs / EQ Library, not in a separate My DAC chooser;
4. current state and editable settings should be one surface, not repeated Overview / Device settings / Edit settings presentations.

The current functional direction already solves the core behavioral versions of these problems. The recommendations below focus on hierarchy, clarity, density, polish, feedback, and accessibility.

---

# 1. Apple

## What to borrow

Apple’s current guidance treats the top toolbar as orientation + a small number of contextual actions, while the tab bar is for switching between major app areas. That maps well to EQ Library: keep the four primary destinations stable and do not overload the top bar with controls that look like they filter library ownership.

Use Settings-style grouped rows for DEVICE and Settings screens: one row communicates the setting name, current value, and disclosure/edit affordance. Avoid a summary row followed by a second duplicate editor section.

Use clear hierarchy rather than decorative chrome:

- strong screen title;
- one concise supporting status line only when status matters;
- grouped lists with predictable row anatomy;
- standard Back behavior for drill-in detail;
- a small number of visible primary actions;
- secondary/rare actions in overflow or lower-emphasis rows.

Use restrained accent color. Brand/accent color should highlight selected navigation, primary actions, important badges, and meaningful status—not every card, icon, border, or label.

## Apple-inspired screen implications

### My EQs

Treat My EQs as the user’s stable personal collection. The title should simply be **My EQs**. The output/target is not part of ownership, so it should not visually dominate the screen title.

Recommended hierarchy:

- title;
- optional compact target/action-context indicator when relevant;
- Needs attention card only when unresolved artifacts exist;
- headphones / Personal EQ / General EQ content;
- row-level actions kept predictable.

A headphone row should feel like a library row, not a settings dashboard. Primary text = headphone/model. Secondary text = selected EQ count or concise status. Optional trailing state = attention/fidelity/action indicator only when it helps.

### My DAC

Device identity + connection status should appear once at the top. Do not repeat Connected / device name in every section.

The **EQ | DEVICE** switch is an appropriate two-pane sibling control. Keep it visually compact and persistent enough that the user always knows which hardware aspect they are viewing.

DEVICE should use a grouped Settings-like list:

`Volume                         42%   >`
`DAC filter               Fast roll   >`
`Gain                         Low      >`
`Amplifier topology          ...      >`

Read-only rows use value text without a misleading edit chevron.

### EQ Library

Search and discovery are the primary jobs. Keep the title/search/discovery structure stronger than target controls. A target indicator may affect compatibility/Flash actions, but should not imply it filters which EQs exist.

### Settings

Settings should be calm and grouped. Preference rows should expose current value directly. Keep diagnostics/provenance/version/attribution lower in the hierarchy than daily preferences.

## Feedback model

Prefer short state changes rather than modal prose:

- `Applying…`
- `Updated ✓`
- `Couldn’t update — device disconnected`

For routine DEVICE settings, do not add a global **Save changes** button merely to imitate a form. If the device transaction applies and persists the value immediately, a second Save concept is misleading.

Where safe and truly reversible, an **Undo** snackbar after verified success is preferable to pretending changes are still pending. If undo itself would be a new hardware write, it must use the same qualified transaction and truthful feedback.

The multi-band EQ editor is different: it intentionally edits a local working copy, so **Review → Apply** plus **Discard changes** is still appropriate there.

# 2. Material

## What to follow directly

Use Material 3 navigation semantics instead of inventing a custom shell. A bottom NavigationBar is appropriate on the Pixel 9 because the app has three to four same-level primary destinations. If the app later targets larger windows/tablets, Material 3 Adaptive can switch to a navigation rail and list-detail layouts without changing the conceptual hierarchy.

Use Material 3 top app bars as screen orientation + core contextual actions. Avoid placing a large text target selector in the same visual hierarchy as the screen title when that selector is only an action/derivation context.

Use Material components and tonal color roles so light/dark themes preserve contrast. Keep interactive touch targets at least Material’s 48 dp minimum even when the visual icon is 24 dp.

## Material-specific recommendations

### Navigation

Compact width:

`My EQs | My DAC | EQ Library | Settings`

No extra top-level destination for vendor/device type. My DAC remains conditional/session-sticky exactly as already approved.

Potential future expanded-width layout:

- navigation rail for primary destinations;
- list-detail presentation for My EQs and EQ Library;
- no change to data semantics.

This is future polish, not required for v0.6 phone release.

### Top app bars

Use a small/medium app bar depending on content density:

- My EQs: title + at most one compact contextual action;
- My DAC: title/device identity + Refresh/overflow only when useful;
- EQ Library: title/search/Refresh as appropriate;
- Settings: title only or minimal actions.

Avoid permanent text buttons that consume the top bar merely to show the active target. A target context chip/compact menu can live below the title or beside an action area when target-specific status actually matters.

### Lists and cards

Prefer flat grouped list surfaces over nested cards inside cards. Cards should represent a distinct object or exceptional state, not every row.

Good card candidates:

- Needs attention;
- disconnected/error state that needs action;
- current DAC EQ summary/response graph;
- update/changelog banner.

Ordinary DEVICE settings should be rows, not independent cards.

### Buttons

Use emphasis by task consequence:

- Filled / prominent: one primary action such as **Flash**, **Apply**, **Recover** when it is the clear next step;
- tonal/outlined: secondary actions such as **Export**, **Reset EQ to flat**;
- text/icon: tertiary actions such as Refresh, More, Hide.

Do not place two equally heavy primary buttons side-by-side unless they genuinely have equal task priority.

### Status and progress

Use inline progress where the task lives. A row being updated can show progress/status on that row instead of blocking the entire screen.

Reserve dialogs for:

- destructive removal/deletion;
- materially level-sensitive hardware changes;
- full EQ Apply review;
- genuinely irreversible/high-risk actions.

Routine filter/balance/mic setting choices should remain direct + verified, as already approved.

# 3. combined

This is the recommended EQ Library direction: native Android / Material 3 mechanics with Apple-like restraint, information density, and settings hierarchy.

## A. App-wide hierarchy

Keep the current four-area model:

`My EQs | My DAC | EQ Library | Settings`

The mental model should be obvious without explanation:

- **My EQs** — what I saved;
- **My DAC** — what is actually on/inside the connected DAC;
- **EQ Library** — find something new;
- **Settings** — preferences and app configuration.

Do not let output-target state blur those roles.

## B. Target context: separate ownership from action

Current code still exposes the active target in the top bar on My EQs/EQ Library. Functionally the library is now device-agnostic, so the visual model should follow.

Recommended direction after approval:

- rename/present it consistently as **Target** or **EQ target**;
- use a compact contextual chip/menu, not a library-filter-looking title control;
- show it only where it affects what the user is about to Export/Flash or how compatibility is described;
- changing it must never navigate away from the currently open headphone/EQ;
- Automatic/connected-DAC context should read as an action destination, not a different library.

Example:

`My EQs`
`Target: Automatic · TRN Black Pearl  ▾`

The second line should be visually secondary. If it is irrelevant on a screen, omit it.

## E. EQ editor blueprint

The EQ editor is the one place where staged changes are appropriate because edits are local until Apply.

```text
Edit EQ
Unsaved changes

[ response graph ]
Band 3
Type      Peak
Frequency 2400 Hz
Gain      +2.5 dB
Q         1.10

Safe · required headroom −4.0 dB

[ Review changes ]
```

Back with unsaved local edits:

- **Keep editing**
- **Discard changes**

Review screen should summarize only actual differences, not repeat protocol/qualification prose.

```text

```

At profile level, the target informs compatibility/Flash—not whether the EQ is discoverable.

For a compatible connected DAC, direct **Flash** sits on the profile/detail action surface. **Add to My EQs** remains separate and does not Flash automatically.

## G. Needs attention blueprint

Root presentation should be compact:

```text
Needs attention · 2                         >`
App-created EQ files need review
```

Expanded/recovery surface:

```text
Legacy preset.xml
Parametric · 10 bands · −4.5 dB
Needs headphone association

[ Recover ]
[ Delete file… ]
```

Recovery form asks only for missing identity:

- Manufacturer
- Model
- EQ name

Then **Recover**. Do not ask for target because recovery creates a device-agnostic Personal EQ.

Malformed/unsupported:

`Can’t recover automatically · Unsupported filter data`

Keep it visible; offer exact owned-file deletion only with confirmation.

## I. Spacing and typography

Recommended system:

- 16 dp page horizontal padding on compact phone layouts;
- 8 dp base spacing rhythm, with 4 dp only for tightly coupled label/value pairs;
- approximately 56–64 dp ordinary setting/list row height depending on supporting text;
- 16–24 dp between semantic sections;
- one dominant screen-title style;
- title/body/label hierarchy from Material typography tokens rather than many custom sizes;
- secondary metadata uses `onSurfaceVariant`/equivalent semantic color, not tiny low-contrast text.

Avoid excessive vertical whitespace that forces routine controls below the fold, but do not compress touch targets.

## J. Icons

Use standard Material symbols where meaning is established:

- My EQs: library/favorite/headphones concept, whichever best matches current product language;
- My DAC: USB/device;
- EQ Library: explore/search/library;
- Settings: settings;
- Refresh: refresh;
- Export: file/download/share-style export icon with text when ambiguity is possible;
- Flash: use text **Flash** alongside any icon because generic hardware-write iconography is ambiguous;
- Delete: delete/trash only for actual deletion;
- Hide: visibility-off only for reversible local hide.

Do not use color alone to distinguish Exact / Optimized / Not suitable or Connected / Disconnected.

## K. Feedback

Use one feedback grammar everywhere:

- idle: current verified value;
- in progress: `Applying…`, `Flashing…`, `Refreshing…`;
- success: concise temporary `Updated ✓` / `Flashed ✓` plus newly read current state;
- stale: `Last read` at section/screen level;
- failure: plain-language result + actual retained/current state;
- never show requested state as current before readback verifies it.

For long operations, preserve navigation where safe rather than using modal blocking spinners.

## L. Accessibility

Mandatory polish targets:

- minimum 48 × 48 dp interactive targets even when icons are visually smaller;
- meaningful TalkBack labels for icon-only actions;
- merge row semantics where a whole row is one action so TalkBack does not announce redundant fragments;
- do not rely on color alone for fidelity, connection, stale, warning, or selected state;
- preserve readable layout at large font scales; do not hard-code row heights that clip Dynamic Type-like enlarged text;
- response graphs always have textual state/filter alternatives and never become the only way to inspect/edit EQ;
- exact numeric PEQ input remains available without requiring slider precision;
- system light/dark/dynamic color roles must maintain accessible contrast;
- loading and verified-success messages that matter should be exposed through appropriate live-region semantics without repeatedly interrupting TalkBack.

## M. Priority order if approved

Recommended implementation sequence after owner approval:

1. clarify target-context presentation without changing ownership/data logic;
2. unify top bars/back behavior and screen title hierarchy;
3. flatten My DAC DEVICE into the final grouped-row visual treatment;
4. standardize row/card spacing, typography, icons and action emphasis across My EQs / EQ Library;
5. polish Needs attention recovery surface;
6. consolidate feedback/status components;
7. accessibility pass and large-font/TalkBack testing;
8. optional adaptive large-screen list-detail work after the Pixel 9 phone experience is stable.

No hardware transaction semantics need to change for these visual improvements.

# 4. relevant references

Official sources reviewed for this blueprint:

### Apple Human Interface Guidelines

- Toolbars — https://developer.apple.com/design/human-interface-guidelines/toolbars
  - toolbars orient the current view and host a deliberate number of contextual actions; tab bars navigate app areas.
- Lists and tables — https://developer.apple.com/design/human-interface-guidelines/lists-and-tables
  - lists express hierarchy/options efficiently; Settings is a canonical grouped-list example.
- Tab views — https://developer.apple.com/design/human-interface-guidelines/tab-views
  - tabs fit closely related mutually exclusive panes with clear short labels.
- Labels — https://developer.apple.com/design/human-interface-guidelines/labels
  - prefer system typography/semantic label colors and legible scalable text.
- Branding — https://developer.apple.com/design/human-interface-guidelines/branding
  - current 2026 guidance recommends restrained accent-color use and preserving platform-native legibility/accessibility.

### Android / Material 3

- Navigation bar — https://developer.android.com/develop/ui/compose/components/navigation-bar
  - suited to three to five equal-importance destinations on compact widths.
- App bars — https://developer.android.com/develop/ui/compose/components/app-bars
  - top app bars provide title, key information, navigation and core contextual actions.
- Material 3 in Compose — https://developer.android.com/develop/ui/compose/designsystems/material3
  - Material color/tonal roles and components provide an accessibility-aware foundation.
