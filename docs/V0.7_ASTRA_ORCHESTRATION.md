## Astra Task 1 — PaperFinder-equivalent EW300 capability crosswalk

**Status:** OPEN

### Objective

Complete an exact-device capability crosswalk for the qualified SIMGOT EW300 DSP fingerprint against every relevant Black Pearl/My DAC capability category, including an explicit independent-volume investigation. Determine which capabilities are safe product features for v0.7 without inheriting behavior from another DAC or from generic KT02H20-family implementations.

### Context & Inputs

- Governing sources: `AGENTS.md`, `docs/CHATGPT_PROJECT_RUNBOOK.md`, `docs/ARCHITECTURE.md`, `docs/V0.6_MY_DAC_APPROVED_DESIGN.md`, `docs/V0.6_MY_DAC_IMPLEMENTATION_PLAN.md`, `docs/V0.7_EW300_DSP_IMPLEMENTATION_PLAN.md`, `docs/V0.7_PRODUCT_SUCCESS_CRITERIA.md`, `docs/V0.7_EW300_DSP_STATUS.md`, `docs/EW300_CAPABILITY_MATRIX.md`, and `docs/EW300_VALIDATION_LEDGER.md`.
- Exact authorized fingerprint: `vid=31b2|pid=111|manufacturer=LE XIAN|product=SIMGOT EW300 DSP|serial=2024-07-03-0000-0000-0000|interface=3`.
- Accepted evidence already establishes the five-band Peak path, reported playback/global-gain state, persistence, guarded Apply/Flash/Reset, and exact-baseline restoration. Do not repeat physical mutation or E001 Save qualification.
- Existing matrix says register `0x66` is verified playback/global-gain state but is not yet an independently qualified standalone playback-volume control.
- Public/reference research may inspect exact-device material and licensed/reference implementations such as `gxcreator/ktmicro-tools`, `jeromeof/devicePEQ`, and other relevant exact-device sources. Generic chipset behavior is discovery evidence only.
- The user wants all real device capabilities supported, but only when exact-device semantics and safety are evidenced.

### Out-of-Scope

- No hardware mutation, Save qualification, Apply, Flash, Restore, Reset, or random register probing.
- No firmware/bootloader/recovery/cross-flash/erase/calibration work.
- No copying commands, ranges, defaults, persistence semantics, or UI controls from Black Pearl, JA11, or a generic KT02H20 implementation without exact EW300 evidence.
- No app code changes in this research task.
- No claim that absence of evidence means the hardware does not provide a feature.

### Acceptance Criteria

- [ ] Enumerate at minimum: native EQ/filter families; band count and unused-band behavior; read/edit/capture/Apply/Flash/Reset/persistence/restoration; standalone playback volume vs global gain; DAC filter; gain mode; amplifier/output-stage topology; balance; microphone/headset controls; UAC detection/switching/help; model/USB identity; firmware/version/update; connection/permission/reconnect/freshness/manual refresh; feedback/safety.
- [ ] Classify every category as exactly one of `SUPPORTED_AND_IMPLEMENTED`, `HARDWARE_DOES_NOT_PROVIDE`, `INSUFFICIENT_EVIDENCE`, or `UNSAFE_OR_OUT_OF_SCOPE`.
- [ ] Use `HARDWARE_DOES_NOT_PROVIDE` only with affirmative exact-device evidence.
- [ ] Resolve whether `0x66` can be promoted to an independent user-facing volume control; family-level documentation alone is insufficient.
- [ ] Review third-party license/provenance before relying on implementation facts.
- [ ] Record any newly supported capability with exact semantics, range/units, read/write direction, persistence/readback, and safety evidence sufficient for implementation.
- [ ] Update `docs/EW300_CAPABILITY_MATRIX.md` only where research materially changes or strengthens current evidence.
- [ ] Close this task immediately after the crosswalk is defensible; any unresolved capability remains `INSUFFICIENT_EVIDENCE` and does not block Task 1 close-out.
