## 4. What changed in this closeout

### EW300 My DAC UX parity

The EW300 now follows the same shared My DAC design language as the existing DACs while remaining capability-specific:

- compact logarithmic EQ response graph;
- 0 dB reference line and active-band markers;
- accessibility description that does not rely on color or the graph alone;
- truthful **Flat**, **Exact saved match**, **Multiple exact saved matches**, **Modified known EQ** only when explicit lineage exists, and **Unknown EQ** states;
- deterministic exact matching from the complete native representation rather than curve similarity;
- explicit **Current hardware EQ** versus **Last read hardware EQ** freshness;
- manual **Refresh** on both EQ and DEVICE through the single authoritative DAC session;
- concise DEVICE state instead of repeated explanation blocks; and
- corrected Personal EQ capture wording: playback/global gain is device state and is **not** part of captured EQ identity.

### EW300 capability closure

Independent research and exact-device evidence support the existing five-band Peak path. No additional DEVICE write was promoted.

`0x66` is corroborated as KT02H20-family digital DAC/playback gain and is already qualified as EW300 playback/global-gain transaction state. The available exact-EW300 evidence does **not** establish a separate end-user volume-control contract, safe independent range, persistence behavior, or standalone-write semantics. Therefore the beta intentionally exposes no EW300 volume slider.

The following remain **INSUFFICIENT_EVIDENCE**, not automatically “unsupported”:

- standalone software volume;
- DAC filter;
- gain mode / PGA;
- amplifier or output topology;
- L/R balance;
- microphone gain/control;
- USB/UAC mode switching;
- firmware/update controls;
- routing/headset configuration; and
- factory-device defaults.

Firmware/bootloader/erase/calibration/recovery/cross-flash work is unsafe/out of scope.

### Shelf-source root cause and fix validation

The historical shelf problem was in finite-hardware target adaptation, not canonical source parsing. The older adapter required source filter families to be natively supported by the target, which is too restrictive for a Peak-only device that can safely approximate a shelf response.

The current representation-v3 path:

1. preserves source low/high shelves unchanged in canonical data;
2. evaluates the complete source frequency response;
3. derives quantized Peak-only EW300 candidates;
4. deterministically selects/refines no more than five Peak bands;
5. preserves source preamp when representable or derives conservative target-side headroom when needed;
6. requires the existing RMS and maximum-response-error gates; and
7. reports **Optimized** or **Not suitable** truthfully rather than silently truncating or rewriting source data.

The regression corpus covers representative OPRA, AutoEQ, community/general, strict text import, Personal EQ, captured-DAC, mixed/over-budget, deterministic-output, canonical-immutability, and unsupported-filter cases. No additional optimizer rewrite was justified after that corpus passed.

## 9. Known beta limitations and intentional boundaries

- Exact qualified EW300 revision/device boundary only; no VID/PID-only broadening.
- Native EW300 product path is five **Peak** bands.
