# EW300 audio-channel investigation and repair plan

**Opened:** 2026-09-24
**Status:** Source root cause identified and guarded fix implemented; exact signed candidate and physical audio confirmation pending
**Priority:** High — owner reports right-channel-only playback and crackling from the left channel at high level
**Scope:** Exact SIMGOT EW300 DSP cable, Android phone, UAPP/audio path, and EQ Library interaction

This document records the owner-approved investigation plan so the audio defect is not lost between
tasks or releases. It is a durable engineering record, not a claim that the app caused the defect
and not a request to repeat already accepted EW300 mutation qualification.

## Owner report

The owner reports that sound is heard only from the right earbud and that the left side becomes
crackly when turned all the way up. The same IEMs reportedly work correctly with another DAC. The
attached screenshots and prior Flash/Reset screenshots are diagnostic evidence only; they do not
authorize a new protocol command or establish a channel-routing cause.

## Source-of-truth and safety boundary

The repository-root `AGENTS.md`, `docs/CHATGPT_PROJECT_RUNBOOK.md`, current maintained EW300
protocol/capability documents, exact remote state, and fresh test evidence govern this work. The
current capability matrix remains authoritative for unsupported or insufficiently evidenced EW300
controls.

Until a root cause is established:

- do not Flash, Reset, Save, Restore, or send exploratory USB output reports;
- do not add a balance, mono/stereo, volume, UAC, or routing control based on inference;
- do not test at maximum volume; begin at minimum level and stop immediately on crackle, heat,
  unexpected loudness, or possible hearing risk;
- do not hide or clear the symptom in the UI;
- preserve the existing no-retry, exact-identity, one-Save, final-readback, and restoration rules;
- preserve the accepted E001 and E037-E046 hardware evidence and do not rerun it merely because a
  later source SHA exists.

The saved checkout is user-owned and must remain untouched. Investigation and any later source work
use an isolated worktree. No physical mutation is part of the initial investigation.

## Confirmed repository facts

1. The EW300 descriptor evidence reports separate USB Audio Class streaming interfaces, including
   stereo playback, and a separate HID interface 3 with interrupt endpoints. See
   `docs/EW300_DSP_PROTOCOL_NOTES.md`.
2. `AndroidEw300UsbTransport` creates an exact-identity HID session. The shared HID session filters
   for the approved HID interface and claims only that interface; it does not select or stream the
   UAC playback endpoints.
3. The application source contains no PCM mixer, `AudioTrack`, `AudioRecord`, AAudio, Oboe,
   channel-mask, left/right balance, or stereo-interleaving implementation. The application
   manifest requests USB host support and internet access, not audio recording or output control.
4. The pre-fix production EW300 codec wrote five PEQ register pairs and, when required by the target
   representation, register `0x66`. It modeled `0x66` as one device-global playback-gain value and
   changed only byte 0 while preserving the other three bytes. PR #30 reads the layout flag at `0x01`,
   writes both low bytes for stereo hardware, and verifies both bytes on final readback.
5. The production EW300 codec has no established left/right, channel-select, routing, or UAC-mode
   command. The capability matrix classifies left/right balance and headset/output routing as
   `INSUFFICIENT_EVIDENCE`.
6. Historical E033 recorded a global-gain change from approximately `-53 dB` to `-57 dB` during
   an incomplete Flash attempt. That proves a real global attenuation change occurred in that
   candidate, but it does not prove or explain a unilateral channel failure.
7. E037-E040 and E043-E046 contain accepted physical Flash, Restore, Apply, Reset, and readback
   evidence for the qualified unit. None of those records qualifies stereo-channel behavior.

### Phase 1 audit result — 2026-09-24

The live `main` branch resolves to `a8abf78275554b44bf2f6a3b0042dfcd8fe8441c`, matching the
owner's installed APK URL suffix `a8abf78`. A read-only comparison of the installed candidate's
source head with the isolated recovery head found no `app/src` code difference; the isolated head
adds only the documentation record for this investigation. The audio-path conclusion below
therefore applies to the installed candidate's production code, not just to an unreleased branch.

The historical branch search found audio/channel/balance implementation only in Black Pearl
control code and generic test fixtures. No EW300 historical commit adds PCM handling, UAC stream
selection, channel masks, or left/right routing. The current indirect-risk surface is limited to
the EW300 PEQ fields, global-gain state, USB HID ownership, reconnect lifecycle, and device
firmware/UAC behavior.

### Owner host-isolation result — 2026-09-24

The owner then connected the headphones/EW300 DSP cable to a computer and observed the same
right-only playback and left-channel crackle. The alternate cable/DAC continued to work correctly.
This result strongly rules out an Android-only, UAPP-only, or EQ Library PCM-routing defect: the
symptom follows the EW300 DSP cable across hosts.

This does not by itself distinguish a physical analog-channel failure, EW300 USB-audio firmware
fault, or persistent DSP state written earlier by a control application. The app can change
persistent PEQ/global-gain device state, so one final read-only register comparison remains useful
if the owner can provide it. The app still has no known channel-specific register or runtime audio
stream path, and no supported software command exists for a factory/firmware recovery.

### Protocol root-cause finding — 2026-09-24

The preserved untouched EW300 stock snapshot records `0x66 = F8 F8 00 00`. The failed Flash
record E033 changed that register to `96 F8 00 00`: only byte 0 moved from approximately `-4 dB`
to `-53 dB`, while byte 1 stayed at approximately `-4 dB`. The exact EW300 descriptor advertises
stereo USB playback, and the reviewed KT02H20 protocol reference defines byte 0/byte 1 of `0x66`
as left/right digital DAC gain for stereo layouts. This explains the owner's host-independent
right-only symptom far better than a runtime audio route defect.

The current production EW300 codec was therefore confirmed to have an app-owned persistent-state
defect: it treated `0x66` as one global byte and changed only byte 0. The source fix reads the
protocol-layout register, writes both gain bytes for stereo hardware, preserves byte 1 for a
single-DAC layout, reads protocol layout as part of the strict baseline, and rejects an unequal
stereo gain pair as one displayable global value. This is a source-level root-cause fix, not yet a
physical audio PASS.

## Ranked hypotheses

The investigation must keep these hypotheses separate:

1. **Persistent EW300 stereo digital-gain state:** leading and now app-owned; E033 shows the
   one-byte write that can attenuate one channel by roughly 49 dB.
2. **EW300 UAC or analog output fault:** remains possible until the corrected two-channel state is
   read back and audio is retested.
3. **EW300 cable/connector/earpiece path:** remains possible if the corrected readback is balanced
   but the symptom persists.
4. **UAPP/Android audio route or channel configuration:** substantially weakened by the computer
   reproduction.
5. **Runtime EQ Library PCM routing:** excluded; the app has no PCM audio path and the failure was
   reproduced outside Android.

The persistent stereo digital-gain write defect is the source-level root cause. A physical audio PASS
is still required to establish that correcting the persistent state resolves the owner's symptom and
to distinguish any remaining EW300 hardware/firmware/cable fault.

## Investigation sequence

### Phase 1 — source and protocol audit

Before any hardware action:

- verify the installed candidate's exact source, version, signer, and APK checksum;
- compare the candidate's EW300 HID/UAC boundary with the current isolated source;
- inspect every `0x66` read/encode/write/restore path, including persisted applied-gain deltas;
- prove the complete write allowlist is the ten PEQ fields plus the documented global-gain field;
- inspect report framing, byte order, signed conversion, and response matching;
- search current and historical branches for audio, stereo, balance, channel, UAC, and gain changes;
- compare against accepted historical behavior without treating historical summaries as instructions.

### Phase 2 — automated safety coverage

If Phase 1 finds an app-owned possibility, add tests before a candidate build for:

- exact EW300 HID report bytes and register allowlisting;
- global-gain signed round trips, boundary values, and preservation of bytes 1–3;
- no left/right or channel-routing writes in Flash, Apply, Reset, Restore, or reconnect paths;
- HID-only interface selection and no UAC interface/alternate-setting ownership;
- flat PEQ and global-gain readback after simulated operations;
- malformed responses, stale sessions, delayed reconnect, and no write/Save replay;
- unchanged Black Pearl, FiiO, library, and offline/error flows.

If the audit finds no app-owned audio path, do not add speculative audio code merely to produce a
candidate APK. Instead, retain the evidence and proceed to the bounded read-only comparison.

### Phase 3 — bounded non-mutating audio comparison

Use the same phone, USB adapter, UAPP version, source track, and IEMs for each comparison. Start at
minimum volume and use a known left/right stereo test recording.

Record only these observations:

1. Android/UAPP balance and mono settings.
2. EW300 with EQ Library closed and no new hardware operation.
3. EW300 after EQ Library performs only a read-only Refresh.
4. EW300 in another available audio player, if available.
5. Known-good DAC with the same phone, player, adapter, source, and IEMs.
6. If the IEM cable permits it, swapped left/right earpiece connections to determine whether the
   symptom follows the earbud or the EW300 output channel.
7. A read-only EW300 capability report containing the complete PEQ snapshot and `0x66` state.

No Flash, Reset, Save, Restore, exploratory write, or maximum-volume test is part of this matrix.
Stop immediately on crackle, heat, unsafe loudness, or any unexpected state change.

### Phase 4 — decision and repair

- If the app writes an incorrect field or gain value, correct the smallest protocol/state defect,
  add regression coverage, and preserve truthful verification. The `0x66` stereo gain write-scope
  defect is now in this category and has a source fix in PR #30; exact-head automated gates passed,
  while trusted-main signing and physical confirmation remain.
- If the app claims or interferes with a UAC interface, correct interface ownership and lifecycle;
  do not alter audio samples or invent a routing control.
- If the failure follows the EW300 independently of EQ Library, do not claim an app fix. Record the
  boundary as an EW300/UAC/analog issue and keep unsupported audio controls out of the product.
- If evidence remains ambiguous, stop at diagnosis and request only the smallest additional
  non-mutating observation needed to distinguish the remaining hypotheses.

The host-isolation result initially pointed to external hardware/firmware, but the preserved raw
register evidence now identifies a narrower app-owned persistent gain defect. No new channel
control is being invented: the fix only honors the existing stereo gain bytes already used by the
device protocol. If the corrected candidate restores equal readback but audio still fails, the
remaining diagnosis returns to EW300 hardware/firmware/cable rather than further app changes.

## Candidate and release gates after a source fix

Only if a source defect is identified and repaired:

1. Run targeted protocol/session/UI tests — complete on PR #30.
2. Run the complete repository, lint, static/security, dependency, emulator, release, and R8 gates
   on one exact source head — complete on PR #30; signing is guarded to trusted `main`.
3. Produce one signed test APK with source SHA, version, signer, checksum, and build variant —
   pending owner-approved integration into trusted `main`.
4. Perform one bounded physical audio confirmation at safe volume, without repeating accepted
   mutation qualification unless a new owner-approved decision requires it.
5. Confirm both channels play normally, no crackle occurs at normal safe listening levels, the
   read-only state is coherent, and previous Flash/Reset verification behavior remains truthful.

No merge, public release, tag, or public EW300 audio-support claim is authorized by this plan.

## Acceptance criteria

The issue is considered resolved only when the evidence identifies the responsible boundary and,
where that boundary is app-owned, the exact signed APK demonstrates:

- left and right channels both reproduce a stereo test signal;
- no unilateral channel loss or crackling at safe normal listening levels;
- no speculative balance/routing control was added;
- genuine USB/session/protocol failures remain visible and fail safely;
- existing EW300 persistence/readback and shared-DAC behavior remain covered;
- the final artifact has reproducible source and signing provenance.

Until then, the correct product status is **EW300 stereo gain-write defect fixed in source;
exact signed candidate and physical audio confirmation pending; no new EW300 audio-support claim**.
