## 1. Goal

Add direct, safe EQ Library support for the USB-C DAC/DSP cable supplied with the **SIMGOT EW300 DSP**. Treat the cable as the hardware target and the EW300 DSP earphone as headphone identity/provenance. Reuse the capability-driven hardware framework introduced for TRN Black Pearl and FiiO JA11 so later hardware additions remain registry-and-adapter work rather than separate product flows.

The implementation work may proceed through software validation and creation of an exact signed candidate. Hardware interaction is limited to one bounded capability-resolution session only if existing evidence cannot answer a necessary question, followed by one consolidated final device session. Merge and public release remain explicit owner-authorization gates.

## 2. Planning evidence and open questions

Available evidence establishes that the EW300 DSP package uses a detachable USB-C cable with an integrated DAC/DSP. Community reports indicate that the stock cable exposes a persistent five-filter parametric EQ that can be read and edited through a compatible browser tool. That is useful discovery evidence, but it is not sufficient authority for a production write implementation.

References available at planning time:

- Product/manual evidence: <https://manuals.plus/ae/1005007541847757>
- SIMGOT Control compatibility page: <https://app.simgot.com/index.php/home/web/appDownload>
- Community five-filter/read-write report: <https://www.reddit.com/r/iems/comments/1rqar9i/you_can_set_a_custom_5_filter_peq_with_the_stock/>
- Community persistence report: <https://www.reddit.com/r/iems/comments/1nrcq2f/eq_questions_simgot_ew300_dsp/>
- Potential protocol references, pending exact-device and license review:
  - <https://github.com/jeromeof/devicePEQ>
  - <https://github.com/gxcreator/ktmicro-tools>
  - <https://github.com/Bukutsu/glacier-eq>

The following facts must be measured or independently corroborated before production writes are enabled:

- exact USB vendor ID, product ID, interfaces, endpoints, report descriptors, and relevant string/firmware identifiers;
- whether all retail hardware revisions use the same identity and protocol;
- transport type and exact read/write/save command framing;
- actual filter count, supported filter types, frequency/gain/Q ranges, and quantization;
- band enable/disable behavior and representation of unused bands;
- availability and semantics of global EQ gain/preamp, bypass, active slot, and reset;
- whether Apply is volatile and whether Save persists across unplug/reconnect and use with another source device;
- readback behavior, error reporting, transaction ordering, and safe recovery after interruption;
- whether the device has any controls outside EQ that can be read or written independently.

No implementation may infer protocol compatibility from a chipset family, web-tool compatibility, or similarity to FiiO/JCALLY behavior.

## 3. Scope

### Included

- one new stable hardware target for the exact supported EW300 DSP cable identity;
- automatic supported-device recognition and Android USB permission handling;
- current hardware EQ readback in the existing **My DAC → EQ** surface;
- response graph, local edit, Review, Apply, verification, and bottom operation feedback through existing shared components;
- deterministic conversion of canonical EQs to the verified native band budget using the shared finite-hardware response adapter;
- explicit Flash from My EQs and EQ Library using the existing flow;
- capture of actual device EQ as a Personal EQ with cable/device provenance;
- Reset EQ to flat only if exact reset/write/save semantics are established and physically testable;
- session-sticky Last read state and automatic refresh after reattach through the current authoritative DAC-session model;
- full automated regression coverage and a signed candidate with a focused hands-on checklist.

### Excluded

- a new navigation model, new My DAC layout, or device-specific UX redesign;
- firmware update, bootloader, recovery, cross-flash, or arbitrary vendor commands;
- SIMGOT account, cloud, web service, or runtime dependency on a browser tool;
- support claims for other SIMGOT products or other cables that merely appear similar;
- a factory-reset claim unless the manufacturer protocol and resulting state are independently established;
- DEVICE controls without exact hardware and safe protocol evidence; any genuinely supported
  control must be added through the shared capability-driven surface;
- copying code whose license or provenance is incompatible with this Apache-2.0 project;
- changing canonical source EQ data to fit the cable;
- merge to `main` or public v0.7.0 release before the owner completes physical qualification.

### Public v0.7 UX exposure

The public candidate must use the approved shared My DAC look and flow. For the exact EW300
profile:

- My DAC → EQ is usable for current/last-read hardware state, response graph, local five-band
  Peak editing, Review → Apply, Peak-only Personal EQ capture, Reset EQ to flat, and verified
  reconnect/final-readback feedback.
- My EQs and EQ Library remain the Flash entry points.
- My DAC → DEVICE reports playback/global-gain state, active Peak-band count, and connection
  freshness. Playback/global gain is not presented as a standalone volume control because that
  independent control is not separately qualified for this fingerprint.
- Unsupported volume, headset, UAC, microphone, firmware, bootloader, and unrelated controls
  remain absent rather than borrowing Black Pearl behavior.
- Read-only capability-report execution/sharing, operation-report sharing, and exact-baseline
  restoration are validation-candidate controls only. They must be hidden from the public release
  build while remaining available to the bounded owner evidence session.

This UX boundary does not broaden protocol support. It only exposes the already-qualified EQ
operations through the established shared flow and removes validation harness controls from the
public product surface.
## 4. Architecture contract

The EW300 DSP work must be additive and use the same extension seams as current hardware support:

1. **Stable registry identity**
   - Add a stable `ExportDevice` entry for the exact hardware target.
   - Keep the persisted ID, display name, hardware-only semantics, selectable status, validation state, and capability profile together in the authoritative output registry.
   - Do not invent a preset-file format. This target remains `HARDWARE_ONLY` unless a separately documented native file format is verified.

2. **Capability-driven DSP derivation**
   - Define one immutable device capability/spec object from measured limits.
   - Reuse the shared complete-response finite-hardware adapter.
   - Preserve a native source band structure when it fits and only native rounding is needed.
   - Fit the complete canonical response when the source exceeds the verified band budget.
   - Reject unsupported filters or quality-gate failures. Never silently take the first five bands, clamp unsafe values, or mutate canonical data.
   - Version representation semantics so stored currentness changes when the device contract changes.

3. **Device-specific protocol boundary**
   - Keep byte/report encoding, decoding, checksums, transaction state, and USB endpoint details in a dedicated EW300 DSP protocol/data adapter.
   - Keep Android USB lifecycle and permissions behind the existing platform boundary.
   - Expose shared domain operations such as connect, read, plan, apply, verify, save, capture, and reset; the UI must not understand wire commands.

4. **One authoritative session**
   - Integrate with the ViewModel-owned DAC session used by My EQs, My DAC, and EQ Library.
   - Do not create a second connection or independent read loop for the new device.
   - Preserve operation generations and stale-baseline protection so delayed responses cannot verify the wrong write.

5. **Shared user-facing behavior**
   - Reuse the approved device header, EQ editor, review, Flash confirmation, capture association, connection states, and bottom operation feedback.
   - Display only values the cable actually reports.
   - Show DEVICE content only for independently verified non-EQ state. If none exists, keep the shared surface truthful and concise rather than inventing settings.

## 5. Execution phases

### Phase A — clean baseline and evidence ledger

- Start a new feature branch from the current `main`; do not continue from the historical v0.6 development checkout.
- Record the exact base commit, app version decision, and current CI baseline.
- Create `docs/EW300_DSP_PROTOCOL_NOTES.md` with source URLs, licenses, observations, hypotheses, confidence levels, and unresolved questions.
- Record community-reported stock values as unverified evidence only. Never use them as a restore target until the owner's device is read and preserved.
- Review any third-party implementation for exact device relevance and licensing before using it. Port behavior from independently supported protocol evidence; do not copy incompatible code.

**Exit gate:** Evidence ledger exists, public references are attributable, and uncertain claims remain explicitly marked.

### Phase B — evidence-first capability resolution

Build and validate the Android-free `Ew300CapabilityBatch` first. It performs only strict, allowlisted read-only checks and exports a small sanitized diagnostic record suitable for attaching to the implementation task. It must not expose unrelated phone data.

Exhaust repository evidence, public research, third-party behavior comparison, captured reports, simulated USB testing, fault injection, and emulator testing before touching hardware. If a necessary product decision remains impossible to resolve, request at most one bounded capability-resolution session from the owner. That session must be signed, baseline-preserving, report-producing, and limited to a predeclared exact-device operation; random probing and guessed persistence commands are prohibited.

If that bounded session is required, capture from the owner's stock cable before any write:

- Android USB identity and descriptors;
- interfaces, endpoint directions/types/sizes, HID report descriptor when present, and audio-control descriptors;
- readable device/firmware strings;
- exact initial EQ state from the known-compatible reference tool and, once decoded, from EQ Library;
- controlled traffic for read, one reversible small band change, apply/save, readback, and restoration of the captured stock state.

Random command probing is prohibited. Firmware, bootloader, erase, and undocumented non-EQ command families are out of scope.

**Owner touchpoint (only if necessary):** Connect the untouched EW300 DSP cable to the Pixel 9 and follow the signed utility's plain-language actions. The utility must stop safely, diagnose failures, and export both reports; the owner must not interpret USB traffic or choose protocol operations. If software evidence resolves the question, skip this touchpoint entirely.

**Exit gate:** Exact supported identity and the minimum safe EQ command set are independently established; the original device state is preserved and restorable.

### Phase C — protocol and capability implementation

- Implement strict command/report models and golden byte fixtures for every supported operation.
- Implement exact response validation, length/type/checksum checks where applicable, timeouts, and explicit failure mapping.
- Implement read current EQ and capture first. Implement stage/apply, persist/save if distinct, and reread verification only when the exact-device evidence gate establishes them.
- Implement flat reset only through the same verified write/save/readback transaction.
- Do not automatically retry mutating commands. A timeout or disconnect produces an uncertain result and requires a fresh read before another write.
- Verify that a successful operation changed only intended EQ state; fail if unrelated readable state changes unexpectedly.
- Add the measured capability/spec entry and target representation version.

**Exit gate:** Protocol unit tests and capability-boundary tests pass without physical-device assumptions hidden in UI code.

### Phase D — existing-framework integration

- Register the exact EW300 DSP cable target and USB matcher.
- Route recognition through the shared DAC session and device-selection policy.
- Reuse existing My DAC EQ state, editor, graph, review, Applying/verification/success/failure feedback, disconnect, and Last read behavior.
- Reuse Flash eligibility and confirmation from My EQs/EQ Library.
- Reuse Personal EQ capture with device provenance and exact-match deduplication.
- Keep global active output and physical connected-DAC identity separate, following the v0.6 contract.
- Add a reset action only if Phase B/C established exact semantics.
- Keep Black Pearl, JA11, and legacy JM12 behavior unchanged.

**Exit gate:** The new target works entirely through existing product flows with no new navigation or device-specific Compose branch beyond truthful capability-driven content.

### Phase E — automated validation

Add meaningful coverage for:

- USB identity matching, supported revision allowlisting, permission denial, detach, replacement session, and reconnect;
- protocol encode/decode fixtures for stock read, changed band, write/apply, save, verification, reset when supported, malformed responses, and explicit device errors;
- exact ranges and quantization for frequency, gain, Q, preamp/global gain, filter types, enable state, and unused bands;
- native preservation, native rounding, complete-response fitting to the verified band budget, generated safe headroom, unsupported filters, and fixed RMS/max-error gates;
- stale baseline, operation generations, delayed response rejection, readback mismatch, disconnect during write, uncertain results, and no automatic mutating retry;
- capture provenance, exact-match reuse, and output-independent My EQs ownership;
- Flash availability/confirmation and shared operation feedback state;
- regression of all Black Pearl and JA11 protocol, DSP, session, and UI contracts;
- migration/persistence behavior for the new stable output ID.

Run targeted tests while implementing, then run each full gate once on the exact candidate head:

- catalog/currentness and priority/source gates;

**Exit gate:** All required checks pass on one exact source commit and the signed artifact provenance is recorded.

## 7. Risk controls

| Risk | Control |
| --- | --- |
| Undocumented or revision-specific protocol | Match exact identity plus verified descriptors/revision evidence; fail closed for unknown revisions. |
| Browser tool appears compatible but does not prove wire semantics | Capture and independently decode read/write/save/readback behavior. |
| Persistent write could erase stock tuning | Read and archive untouched state first; use one reversible change; prove restoration before broader tests. |
| Five-band report is incomplete or wrong | Derive capabilities from device observations and strict fixtures, not community wording. |
| Apply and Save semantics differ | Model them separately only when evidence proves the distinction; verify persistence explicitly. |
| Interrupted transfer leaves uncertain state | No automatic mutating retry; reconnect and fresh-read before any subsequent write. |
| Third-party reference license is incompatible | Maintain provenance ledger; use only license-compatible code or independently documented behavior. |
| Device-specific code spreads through UI | Keep identity/capabilities/protocol in registry and adapters; consume shared domain/session contracts. |
| New support regresses qualified hardware | Keep existing adapters unchanged and require Black Pearl/JA11 regression gates. |
