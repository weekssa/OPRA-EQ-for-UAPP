# v0.7 EW300 DSP status

**Updated:** 2026-09-19
**Recovery branch:** `feature/v0.7-ew300-recovery`
**Base:** current `main` at the start of recovery
**Product state:** software-prepared beta candidate; exact-device hardware validation pending
**Public release:** not supported by v0.6.0 and not released in v0.7.0

## Current decision

The SIMGOT EW300 DSP cable is being added as another DAC through the existing registry, finite-hardware adapter, shared ViewModel-scoped session, My DAC shell, Flash surfaces, and Personal EQ capture path.

The recovery branch does not claim that the final hardware behavior is qualified. The user-visible product must continue to identify EW300 as **Hardware validation pending** until the exact signed beta passes the consolidated owner session.

## Evidence already available

The preserved evidence from PR #21 and its discovery history establishes:

- exact observed identity: VID:PID `31B2:0111`, revision `0101`, manufacturer `LE XIAN`, product `SIMGOT EW300 DSP`;
- HID interface 3 and the captured 74-byte report descriptor;
- vendor report IDs `0x4B` and `0x54` with 10-byte input/output payload declarations;
- exact read framing using report `0x4B`, command `0x52`, and register echoes;
- a preserved untouched stock snapshot containing the current slot, five observed band pairs, and a global-gain payload;
- volatile gain/frequency/Q raw-field write, readback, exact restoration, and final full-snapshot matching on the owner’s cable;
- reversible raw filter-code experiments for codes 1–4 with exact restoration; and
- Android diagnostic launchability hardening, including DEX class-definition and cold-launch checks.

These facts qualify the observed raw transport boundaries. They do not, by themselves, qualify acoustic units, full ranges, persistence, Reset, or every retail revision.

## Capability decision table

| Capability | Evidence status | Product decision in this beta |
| --- | --- | --- |
| Exact USB identity | High confidence for the observed identity/revision | Allowlist only the verified VID/PID and exact supported interface behavior |
| Five raw band pairs | Exact transport/readback evidence | Support guarded five-band readback and domain representation |
| Frequency units/range | Public decoder plus owner raw-field evidence; semantic range remains bounded | Use only the documented codec limits; fail closed outside them |
| Gain units/range | Raw tenths-dB behavior observed; full boundaries not physically established | Use bounded codec limits; no silent clamp |
| Q units/range | Raw thousandths behavior observed; full boundaries not physically established | Use bounded codec limits; no silent clamp |
| Filter types | Raw codes 1–4 reversible; acoustic labels remain provisional | Expose only mappings backed by the final qualification; otherwise reject/omit |
| Disabled/unused bands | Not independently established | Do not invent disabled-band semantics; require complete representable bands |
| Global gain/preamp | Register observed; write/persistence mapping remains gated | Keep Flash/editor gain behavior behind one-time exact-device qualification |
| Commit/persistence | Candidate code has a guarded transaction; final device persistence is not yet qualified | Do not call it saved/persistent until power-cycle evidence passes |
| Reset | Software transaction exists but final target state/persistence is not qualified | Keep Reset pending/disabled unless the final physical gate passes |
| Other DEVICE controls | None established | Show a truthful no-additional-controls state |

## Remaining hardware gate

No additional discovery loop is planned. If software tests cannot resolve a necessary question, the only allowed research session is a single signed, baseline-preserving capability-resolution test. Otherwise, combine the required gain/persistence/reset checks with the final beta validation session.

The owner is not asked to test until:

1. all software and security gates pass on one exact source commit;
2. the APK package, signer, checksum, and launchability are verified;
3. all unsupported capabilities are explicitly absent from the UI; and
4. one concise product-language checklist is ready.

## Current implementation boundary

The beta candidate may contain guarded software paths for the observed five-band transport and the proposed gain-aware transaction, but the UI and output registry must label the target **Hardware validation pending**. No public release claim is made. No factory-reset claim is made. No Black Pearl control is copied to EW300.

## Evidence provenance

The detailed raw evidence ledger remains in `docs/EW300_DSP_PROTOCOL_NOTES.md`. PR #21 remains open/draft and is preserved as the source history. The separate discovery APK/tooling is not part of the shipping recovery branch; future discovery, if ever needed, belongs in an explicitly non-production diagnostic surface.

## Exit condition

This status can change to hardware-qualified only after the exact candidate records a physical PASS for the applicable EW300 read, edit, Apply, Flash, reconnect, capture, persistence, and Reset behavior, with every result tied to the exact source commit and signed APK. Merge and release still require explicit owner authorization.
