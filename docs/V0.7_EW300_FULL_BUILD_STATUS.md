## Full-build implementation completed in this continuation

- Added a versioned EW300 capability profile with exact manufacturer, product, interface, and
  qualified serial fingerprint checks. VID/PID alone cannot authorize a mutation.
- Promoted only the evidence-backed five-band Peak path to the qualified product capability
  catalog. Playback gain remains device state and is not part of a captured EQ profile.
- Removed the Save qualification action from the normal product UI. The historical qualification
  plumbing remains only for evidence/report compatibility and tests.
- Added the shared strict baseline and volatile-restoration coordinator used by EW300 mutation
  paths. It requires four-byte reads for the complete read-only register set, never retries a
  write, and never commits a restoration.
- Changed EW300 editor Apply to use the persistent Save command once, then require fresh final
  band and gain readback.
- Enabled the exact-profile EW300 Flash and Reset product paths behind the existing Direct Flash,
  active-target, connection, and exact-fingerprint gates.
- Updated user-facing wording so the app distinguishes the verified EW300 Peak path from
  unsupported Black Pearl controls and from unsupported firmware-level operations.
- Added unit coverage for exact profile authorization and updated flasher tests for the shared
  strict transaction boundary.

## Software work still required before owner hardware testing

The new head must pass one coherent release validation cycle. The local checkout has no Gradle
wrapper or system Gradle executable, so Android validation must run through the repository’s
GitHub Actions workflows after the implementation branch is published. Required gates are:

1. Android unit tests, lint, debug assembly, and release assembly.
2. EW300 protocol, capability-profile, optimizer, readback, Apply, Flash, Reset, reconnect, and
   failure-path tests, including no automatic retry after an uncertain mutation.
3. Compose UI/emulator validation for the exact-profile UI and the absence of the Save
   qualification action from ordinary product builds.
4. Black Pearl and FiiO regression tests, catalog-currentness, priority-community coverage,
   dependency submission, CodeQL, and patch-integrity checks.
5. A signed beta built from one exact source SHA, with the repository-pinned signer, package and
   version metadata, APK digest, signature schemes, alignment, source-SHA display, installation,
   and cold-launch checks recorded.

No physical testing is requested until all of these gates pass.

## Physical validation boundary after software gates

There will be one consolidated owner session using the exact signed APK. The session will use only
the app’s labeled controls and will cover read-only preflight, exact-device identity, Peak-only
Apply, readback/capture, Flash if enabled, full power removal/reconnect, Reset only if enabled,
reconnect recovery, and the retained Black Pearl regression checks. The already completed Save
qualification is evidence and is not repeated.

The owner must stop and export both readable and JSON reports on an unexpected identity, warning,
crash, failed restoration, outside-instruction disconnect, or `UNCERTAIN`. An uncertain mutation
is diagnosed before any retry; the app never retries it automatically.

## Intentionally unsupported

This build does not authorize volume, headset, UAC, microphone, other Black Pearl controls,
firmware, bootloader, erase, calibration, recovery, cross-flash, unknown EW300 revisions, or
compatibility claims based only on a chip family or VID/PID. “Fully functional” means only the
exact EW300 Peak EQ feature set verified for the qualified fingerprint and signed candidate.

After software gates and the consolidated hardware session pass, update PR #23 and the maintained
documentation with the signed artifact and hardware reports. Keep PR #23 in draft. Merging,
publishing a release, and making a public EW300 support claim require separate explicit approval.
