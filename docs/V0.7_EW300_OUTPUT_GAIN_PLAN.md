# v0.7 EW300 output-gain control plan

**Decision:** implement a conservative EW300 output-gain control through the existing shared
session/mutation architecture, then require one bounded owner physical confirmation on an exact
signed candidate before treating the capability as physically qualified or making a public claim.

## Evidence and boundary

- The current EW300 readback already exposes the verified playback/global-gain field at register
  `0x66`, using the advertised single-DAC/stereo layout from protocol flags.
- Stereo writes must update both active low-byte channels and must fail closed when the baseline
  channels are unequal. The existing EQ Flash/Reset/Apply guards remain authoritative.
- The wire range is signed half-dB steps (`-64.0 dB` through `+63.5 dB`), but the user-facing
  control exposes only `-64.0 dB` through `0.0 dB` in `0.5 dB` steps. No positive boost is exposed.
- The requested value is the resulting hardware output gain. EQ Library's playback-gain delta is
  stored separately from the user baseline so later Flash/Reset does not double-apply or erase a
  manual level adjustment.
- A mutation is allowed only for the existing exact EW300 fingerprint and only through the one
  authoritative EW300 session/mutation gate.

## Implementation contract

1. Read the complete current EW300 baseline and protocol layout.
2. Reject missing/incomplete reads, unequal stereo gain, stale session, invalid range, or unknown
   exact identity before writing.
3. Write the gain register once, read it back, and require an exact volatile match.
4. Send at most one existing EW300 Save command.
5. Require the existing same-session or exact replacement-session boundary.
6. Perform bounded read-only final gain readback; publish success only on an exact match.
7. Persist the user baseline separately from the EQ-applied delta only after verified success.
8. Preserve an uncertain result and block implicit mutation replay; allow only the existing
   read-only reconciliation path after a verified replacement session.

## UX contract

- The DEVICE tab shows the current verified output gain and makes the row actionable only when the
  readback is current.
- A Material dialog stages one absolute gain value with a 0.5 dB slider and requires explicit
  “Save and verify” confirmation.
- The dialog warns that the change can make audio much louder and instructs the owner to keep
  Android volume low during testing.
- Busy, stale, disconnected, transfer-failed, and verification-failed states remain visible;
  the UI never converts an uncertain result into success.

## Automated acceptance gates

- Protocol/descriptor tests prove the conservative range and 0.5 dB quantization.
- Flasher tests prove successful stereo write + one Save + final readback, positive-boost rejection,
  unequal-stereo fail-closed behavior, and uncertain-Save reconciliation without a second Save.
- Existing EW300 protocol, Flash, Reset, Apply, reconnect, R8, emulator, lint, security, and
  release gates must remain green on the exact candidate head.
- The exact signed artifact must carry its source SHA, version `0.7.0` / code `7`, pinned signer,
  checksum, and install/cold-launch evidence before physical testing.

## Single bounded physical test still required

Owner action is needed only after the exact signed candidate is ready:

1. Connect the exact previously qualified EW300 and confirm the current gain readback.
2. Start with Android/system volume low. Open DEVICE → Output gain and move from the current low
   value to a modest test value, such as `-40.0 dB`; confirm the app reports Save and final
   readback verified.
3. Confirm both channels play, increase only in small steps as needed, and stop immediately for
   crackle, imbalance, unexpected loudness, disconnect, or any unverified/error state.
4. Refresh/reconnect and confirm the selected level persists.
5. Flash or Reset only if the test plan specifically asks for the existing accepted EQ flow; do
   not repeat accepted Flash/Reset/Apply/Save qualification solely for this control.

The result must be recorded against the exact signed APK, checksum, signer, hardware fingerprint,
and operation evidence. Until that record exists, this remains a candidate implementation and not a
public EW300 standalone-volume support claim.
