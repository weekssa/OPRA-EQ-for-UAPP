# v0.7 Product Success Criteria and Closeout

**Purpose:** This is the acceptance contract for the owner's goal: a finished v0.7 with a polished, consistent My DAC experience; every exact-device capability that is both real and safely evidenced; and reliable handling of source EQs whose filters do not match a target device.

This is a scope/acceptance definition, not a claim that each item is already implemented or physically qualified. Current status lives in `V0.7_EW300_DSP_STATUS.md`, append-only evidence in `EW300_VALIDATION_LEDGER.md`, and live-head artifact/check links in PR #23. A new commit changes the candidate SHA; only checks and artifacts for that exact SHA are current.

The independent release audit is `docs/V0.7_RELEASE_READINESS_AUDIT.md`. It records concrete
source-safety corrections and unresolved acceptance gaps; no corrected-source signed test APK is
available yet.

## Product promise

“Parity with Black Pearl” means consistent flow and a complete feature-by-feature capability review—not identical hardware controls. Reuse the shared My DAC shell, navigation, editor/review, capture, Flash, Reset, connection/freshness states, visual language, feedback, accessibility, and recovery behavior. Add a hardware control only when its exact device profile and behavior are evidenced and safely implemented. Never inherit Black Pearl commands, ranges, persistence, reset semantics, or controls by analogy.

Mutation remains limited to the internally allowlisted qualified unit, including VID/PID,
manufacturer/product, the recorded USB revision, serial, and interface. Do not publish the
unit-unique serial. Unknown revisions are read-only.

## 1. My DAC cross-device UX

Every supported DAC uses one app-wide authoritative session shared by My EQs, My DAC, and EQ Library. The app preserves output-independent My EQ ownership and does not silently change the active output when a device is inspected. My DAC retains two tabs—EQ and DEVICE—and does not add a second EQ chooser.

Acceptance:

- Text—not color alone—distinguishes connecting/loading, connected/current, disconnected/Last read, stale, permission needed/denied, refreshing, applying/flashing, re-enumerating, verified success, mismatch, and uncertain/failure states.
- A successful connect/reconnect refreshes real EQ and DEVICE state through the shared session. A compact manual **Refresh** remains available for external changes and uses that same authoritative session.
- EQ overview shows actual current/Last read state, a compact log-frequency graph with active-band markers and 0 dB reference, and only defensible classifications: Flat, exact saved match, modified known EQ, or unknown EQ. Curve similarity alone never establishes lineage.
- Edit stays local until reviewed. The review presents exact representable values, complete-response/headroom safety, device limits, and what will change before explicit Apply. Only final hardware readback establishes success.
- Captured state becomes a Personal EQ with native values and truthful device provenance; no unrelated playback gain, invented authorship, or silent association.
- EQ choice remains where the EQ lives: My EQs and EQ Library provide guarded Flash; My DAC has no duplicate chooser. Confirmation shows target, fidelity/adaptation, band count, headroom/playback consequences, and genuine cautions.
- Reset EQ to flat is separate from factory reset or exact-baseline restoration. Baseline restoration/report tooling is validation-only and absent from public builds.
- DEVICE is one concise capability-driven settings surface with screen-level current/stale status. Only genuinely supported/editable controls get rows/actions. Validation buttons do not ship.
- Accessibility remains usable without the graph or color: semantic values, labels, large text, focus order, and TalkBack. Errors and recovery give a safe plain-language next step.

## 2. Black Pearl feature crosswalk

Use the approved My DAC design and Black Pearl capability/profile records to enumerate and individually classify every relevant category for EW300. Minimum categories: native EQ/filter families, bands and unused-band behavior, read/edit/capture/Apply/Flash/Reset/persistence/restoration; standalone playback volume versus reported global-gain state; DAC filter; gain mode; amplifier/output-stage topology; left/right balance; microphone functions; USB audio/UAC mode detection or switching/help; model/USB identity; firmware/version/update; connection/permission/reconnect, freshness, manual refresh, feedback and safety.

Each capability is one of: supported/implemented, hardware does not provide, insufficient evidence, or unsafe/out of scope. “Hardware does not provide” requires affirmative evidence; lack of evidence is not proof of absence. The matrix currently supports only the exact EW300 identity and five-band Peak transaction path plus the separately reported playback/global-gain state. Register 0x66 is not thereby an independently qualified volume control. Other unestablished controls stay absent and marked **insufficiently evidenced**. Unknown revisions, firmware/bootloader/recovery, erase, calibration and cross-flash remain outside this release.

## 3. Low/high-shelf conversion

The user's low-shelf concern is a shared conversion-quality goal, not native EW300 shelf support. Validate the source-neutral derivation for representative EQs from OPRA, AutoEQ, community/general sources, imports, Personal EQs, and captured DAC EQs across outputs that use the optimizer.

Acceptance:

1. Preserve immutable canonical source data; alter only a derived target representation.
2. Fit the complete combined response on the defined frequency grid, including interactions among shelves and peaks.
3. Enforce deterministic documented RMS/max-error, headroom/safety, and target-range gates; never silently drop/clamp filters or invent Q/slope.
4. Label a passing conversion **Optimized** and show honest fidelity/caution in review. A failed gate is **Not Suitable** (or existing equivalent) and blocks unsafe Flash.
5. Add golden/corpus tests for low-shelf frequency/gain/Q ranges, mixed shelves and peaks, source families, edge values, round-trip determinism, and canonical-source immutability. Add sanitized fixtures for the concrete failures the owner reported when available.
6. Keep EW300 native readback/capture/edit/Flash/Reset Peak-only. An approximation to five Peak bands never proves native shelf semantics.
7. Never re-export stale UAPP/ToneBoosters XML after source compatibility or generation fails.
   Keep an exact existing app-owned UAPP file under **Needs attention** as unsupported and
   non-recoverable until explicit user removal; do not silently delete it or affect other targets.

Do not claim “fixed for most EQs” from one EW300 profile or one synthetic case. Close this item after corpus tests and output regressions pass.

## 4. Engineering and release gates

Preserve exact identity; one authoritative session; permission-before-write; complete baseline; qualified bounded writes only; volatile readback before exactly one Save; no write/Save retry or mutation replay; reconnect gate; exact replacement fingerprint and newer generation after detach; mandatory final readback; exact restoration where required; uncertainty on incomplete evidence; truthful measured-versus-null telemetry.

New Favorites and General EQs must persist the full canonical profile plus the selected immutable
revision and source references; adapters derive compatibility projections. Save-time resolution
must be exact, multi-item General EQ saves must be atomic, and a non-destructive migration must
leave legacy rows projection-only rather than fabricate source history.

On one coherent source SHA, pass focused/unit/protocol/session/repository/UI tests, full Android unit tests, lint, debug/release assembly, connected emulator/UI, accessibility/offline/error states, and regressions for Black Pearl, FiiO JA11, shared session, My EQs, and EQ Library. Verify clean install and in-place upgrade for the signed release.

The signed candidate must bind the same exact SHA to package `com.weekssa.opraeqforuapp`, versionName `0.7.0` / versionCode `7`, APK SHA-256, pinned signer SHA-256, APK alignment/signature, signed install and cold launch, immutable artifact and artifact digest. Also pass Android CI, CodeQL, catalog currentness, priority coverage, and dependency submission. The live PR and ledger own current values; never carry a prior candidate's checksum forward.
