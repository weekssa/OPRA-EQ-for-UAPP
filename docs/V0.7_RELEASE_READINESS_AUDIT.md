## Bounded implementation corrections

The reviewed patch set adds or changes only these safety/readiness boundaries:

- Include the recorded USB device revision in EW300's exact mutation fingerprint. Other revisions
  may remain discoverable/read-only but must not inherit write authorization.
- Restrict EW300 write encoding to the physically qualified Peak filter. Shelf responses remain
  eligible for source-to-target optimization, but shelf wire filters cannot be encoded by Apply.
- Redact the unit-unique serial in shareable readable/JSON operation and capability reports while
  keeping the complete internal fingerprint for authorization.
- Add defense-in-depth exact-revision authorization to the retained Save-qualification service,
  require a Peak-coded first band before its first write, and hard-disable Save qualification in
  release builds. E001 already closes the physical qualification; this path is not enabled for
  another physical run.
- Redact the known unit serial from failure text as well as fingerprint fields in shareable
  reports; exception text is not trusted as privacy-safe.
- Enable release R8 minification and require a non-empty mapping that proves at least one
  application class is renamed.
- Make signed candidate workflows manual and main-only; do not expose signing secrets or checkout
  credentials to feature-branch Gradle/build code. Run the R8 verifier before signing secrets are
  present. Verify alignment after signing and publish exact source/package/version/signer/checksum/
  R8 provenance.
- Remove the duplicate `with:` key in the signed release-candidate workflow and disable its unsafe
  public-publish mode. Public publication must wait for a separately reviewed exact-artifact
  promotion workflow that verifies the tested candidate bytes; this change creates no tag or
  release.

These changes do **not** authorize repeating E001 or any physical read/Apply/Flash/Restore/Reset
session. The accepted physical results remain tied to their historical source SHAs in the

## Acceptance gaps found; do not call v0.7 complete

- Personal/import/captured EQ persistence and several conversion entry points still use the legacy
  `OpraEqProfile` shape. The architecture contract requires source-neutral canonical EQ ownership;
  a compatibility projection is not sufficient evidence that storage and all consumers preserve
  the canonical source representation. Resolve with focused architecture review/migration tests,
  not an unreviewed broad model rewrite.
- OPRA adaptation uses `mapNotNull` for malformed/missing filter fields, and the non-strict
  parametric text parser skips malformed active filter lines. A partial EQ can therefore be
  represented without an explicit incomplete/error state. Fail closed or prove complete-source
  parsing before claiming malformed/unsupported filters are preserved.
- The ToneBoosters converter limits output to ten bands and describes them as “priority-sorted,”
  but no authoritative source priority field/order contract was verified. Establish the actual
  UAPP/ToneBoosters parity rule and add fixtures; do not reorder or truncate by guess.
- The previous connected tests ran on API 35, not the app's minimum API 26. A min-SDK smoke test,
  clean install, and v0.6.0 in-place-upgrade/data-preservation test remain product gates.
- Public tag/release publication is deliberately disabled. A future publisher must promote the
  exact previously tested artifact by immutable run/artifact identity and recheck its manifest,
  recomputed hash, signer, package/version, and alignment; same-source rebuild is not proof of APK
  byte identity.
- Accessibility, offline/error/reconnect flows, complete cross-DAC Black Pearl/JA11/JM12
  isolation, and the My EQs review/cancel route have not all been verified against a corrected
  signed candidate. Code-level/unit coverage is not physical or complete product verification.
- Security review found the old signed-beta workflow ran for feature-branch pushes with write
  permission and exposed the release keystore before branch-controlled Gradle execution. No
  secret exfiltration was evidenced. The revised main-only/manual workflow is an intentional
  owner-controlled integration gate; it cannot produce a corrected candidate until the code is
  integrated into trusted `main` with explicit owner authorization. A later independent review
  also found and this audit repairs a stale persistence-qualification build flag, missing exact
  identity/Peak guards in its callable service, report failure-text privacy leakage, and a duplicate
  YAML key. These last repairs invalidate any CI run on the earlier `987b580` source.
- The Git remote's push response during this audit reported 51 Dependabot vulnerability alerts on
  the default branch (3 critical, 20 high, 26 moderate, 2 low). This is an alert-count banner, not
  a source-specific triage: exact packages, reachability, and applicability to v0.7 were not
  available through the read-only connection. Security is not closed until the owner/reviewer
  triages those alerts against the release dependency graph and documents disposition.

### Source-order evidence clarification

The official OPRA `eq_info.json` schema at commit
[`0b88ecd4e2bef7cf69fd5d50f1d06fb586c10865`](https://github.com/opra-project/OPRA/blob/0b88ecd4e2bef7cf69fd5d50f1d06fb586c10865/schemas/eq_info.json)
defines `parameters.bands` as sorted by priority and explicitly directs limited-band software to
truncate the list. This supports the first-ten selection rule only when the app's trusted adapter
has verified OPRA provenance. It does not authorize truncation of arbitrary UAPP, imported,
Personal, community, or mixed-source band lists, and it does not establish ToneBoosters mobile
behavior beyond the repository's existing converter contract. Those cases remain fail-closed when
priority cannot be proven.

The additional repository-level instrumentation regression now changes the managed source to an
unrepresentable 11-band profile while the exact app-owned export is being read. The subsequent
transaction-time guard must reject recovery before saving a Personal EQ or changing the ownership
row. Independent review also found that repeated Recover taps could create duplicate Personal EQs;
the dialog now disables duplicate submissions, and the repository returns the existing linked
Personal EQ on repeat requests, including a transaction-time race. These Room instrumentation tests
are part of the exact-head Android CI gate and are not locally executed in this environment.
