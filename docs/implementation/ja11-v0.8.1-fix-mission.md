# 2. PHASE-1 EVIDENCE — DO NOT REOPEN WITHOUT INVALIDATING EVIDENCE

Treat the completed JA11 Phase-1 handoff as the starting evidence.

Important conclusions:

## Microphone/headset false-negative — PROVEN

For one physical Off -> On restoration:

- the complete 10-byte command write finished;
- physical detach occurred during the transport's 200 ms settle interval;
- the old session became stale;
- the app returned `StaleBaseline`;
- the replacement session freshly read the requested state as applied;
- the write was not retried.

Therefore:

**completed write + expected restart during settle must not automatically become a failed logical operation.**

## UAC replacement-session flow — PROVEN

Both UAC directions physically worked in Phase 1.

The JA11 changed between:

- `2972:0102`
- `2972:0101`

Each successful transition:

- returned a reconnect-required result;
- re-enumerated;
- used a new session;
- freshly verified the requested UAC state.

Use this path as a regression/reference implementation.

## Stale-session reuse

Four physical detach/attach cycles opened replacement sessions.

No stale-handle reuse was physically reproduced.

Do not claim stale reuse caused the observed false-negative.

Nevertheless, production invariants must forbid old-session continuation after detach.

## Latent permanent-busy defect

Current source evidence established that a terminal restart-verification failure can retain `pendingRestartWrite`, while `isBusy` remains true whenever that value exists.

Fix this terminal-state defect.

## Volume

Runtime setter/readback is proven.

Volume survived the reset/re-enumerations generated by microphone/UAC changes.

True loss-of-power persistence remains unresolved by Phase 1.

The owner separately observes a physical unplug returning volume to 60.

Do not invent a persistent-volume command.

## Active program

Runtime program selection/readback is proven.

Off survived reset/re-enumeration in Phase 1.

The owner separately observes a physical unplug returning the JA11 to User 1.

True power-on/startup semantics remain unresolved.

Do not invent a startup-program setter.

## Custom EQ Flash

Current production sequence already:

1. reads baseline;
2. writes five filters;
3. writes global gain;
4. selects User 1;
5. applies;
6. verifies pre-Save target;
7. sends one Save;
8. handles restart if generated;
9. performs authoritative final verification.

There is no software starting-state requirement that User 1 already be active.

Do not add a preliminary reboot.

Do not add a second automatic Save.

No evidence establishes it as a general Device-state commit.

# 12. REQUIRED TRANSPORT DESIGN

The implementation must distinguish a synchronous USB transport call from the logical JA11 operation.

Conceptually distinguish outcomes such as:

- full report completed and device remained available;
- full report completed and an expected restart/detach followed;
- report definitely rejected/incomplete;
- transport completion uncertain;
- stale generation before safe acceptance.

Exact enum/class names are implementation choices.

### Critical rule

If the complete intended output report is known to have been accepted/written and the JA11 then performs a restart expected for that operation:

do not convert the operation into an ordinary transport failure merely because the device disappears during settling.

### Equally critical rule

Detach by itself does **not** prove success.

If full report completion is unknown:

- do not classify the mutation as successful;
- do not replay it;
- enter an uncertain/recovery flow.

# 13. EXPECTED-RESET STATE MODEL

`START`

-> issue command
-> establish report completion
-> `EXPECTED_RESET`

-> wait for exact JA11 family
-> reacquire permission/session
-> perform authoritative fresh read
-> compare against request
-> `SUCCESS`

or a verified failure/recovery result.

Do not merely suppress exceptions.

Fresh readback determines final success.
