# FiiO JA11 v0.8.1 — identity design decision

> Historical design decision. Model D was approved and is now implemented in the mission worktree;
> Present-tense references to the source describe the 2026-10-09 preimplementation snapshot. See
> [the current-state report](ja11-v0.8.1-current-state.md) for implementation and gate status.

**Date:** 2026-10-09
**Scope:** Off-phone source/history and Android API review only. No production code, tests, builds, ADB, or device access were used for this decision.
**Recommendation:** **Model D — session-specific identity requirements.**

1. **How v0.8.0 identified, opened, and reacquired the JA11.**
   In the v0.8.0 tag, AndroidKt02h20HidSession.kt matched the configured VID/PID, requested Android USB permission, opened the current UsbDevice, claimed its supported HID interface, and recorded a fingerprint. The fingerprint read device.serialNumber best-effort and used .orEmpty(); it did not reject an empty value. For Mic/UAC restart controls, FiioJa11ControlRepository.kt retained the requested control, prior session generation, and baseline; verification required a later session generation and fresh snapshot/readback, without comparing a serial identity. The JA11 Flash path also had no mandatory serial check. See the tagged session and repository sources.

2. **Whether v0.8.0 required serial.**
   No. Serial was optional metadata for initial connection, reads, same-session volume/program changes, Mic/UAC writes, and Flash/Save. The Mic/UAC verifier required a new session and authoritative readback, not a serial match. This is the compatibility baseline relevant to J024.

3. **Exact change that introduced the current serial rule.**
   Commit [a78808443c71d688e0f338e96495847569fe12f7](https://github.com/weekssa/OPRA-EQ-for-UAPP/commit/a78808443c71d688e0f338e96495847569fe12f7), “Fix JA11 restart verification across re-enumeration,” added data/kt02h20/FiioJa11DeviceIdentity.kt and wired it through AndroidFiioJa11UsbTransport.kt and FiioJa11ControlRepository.kt. The helper requires exactly one nonblank serial= field in the session fingerprint, then drops pid and interface before comparison. The control repository requires that key before sending restart-classified Mic/UAC writes and requires an equal key on the replacement session.

4. **Why it was introduced.**
   J019 physically showed a completed Mic write and successful fresh readback while the automatic verifier timed out; the observed HID interface ID changed 3 → 2 → 3, but the app’s selected interface was not recorded. Cancellation of the earlier verifier was also plausible. The commit addressed verifier ownership and PID/interface changes, while adding serial as a conservative guard against attributing a replacement session to another physical unit. It was not prompted by an observed wrong-device mutation.

5. **Whether the motivating wrong-device risk was observed.**
   No recorded JA11 evidence shows a second device being selected, a physical swap, or a write reaching the wrong unit. J019 is a real false-negative verifier result with candidate explanations, not wrong-device evidence. J020 records a completed Mic write, delayed permission, a fresh replacement session, Mic Off readback, and unavailable replacement identity; no swap or wrong-device event was observed. J016/J017 and Phase 1 recorded successful older-candidate reconnect/readback/restoration, without proving serial availability. The wrong-device threat is a valid design risk, but historically hypothetical.

6. **What J024 proves about serial.**
   On the exact tested diagnostic candidate, Android USB permission was granted, the JA11 HID session opened, HID reads and a complete EQ snapshot succeeded, and both UsbDevice.getSerialNumber() and the opened UsbDeviceConnection.getSerial() returned null. The identity gate stopped before any write. J024 does not show whether the raw USB descriptor has iSerialNumber = 0 or whether Android failed to return the string; that distinction would not create a usable stable identifier by itself.

7. **Exact safety property the current serial key provides.**
   For Mic/UAC expected-restart verification, equality of a nonblank serial field helps reject a replacement session whose reported serial differs from the session that received the write, while allowing PID and interface changes. The helper’s “exactly one” check means one serial field inside that fingerprint; it does not enumerate attached units or prove that the serial is globally unique, immutable, authentic, or unspoofable. Today the pre-write check blocks Mic/UAC restart writes on a serialless JA11 even when the current session opens and reads. It does not block ordinary reads or same-session controls, and it is not applied consistently to Flash/Reset.

8. **Lifecycle protections that already prevent stale-session errors.**
   The current source has unique permission-action UUIDs and request IDs, one active connect attempt, callback checks for request/device/PID/detach generation, fresh UsbManager.deviceList resolution before open, current permission recheck, session and detach generations, old-connection closure, a transaction token and pending-write owner, a bounded restart watchdog, terminal cancellation, no uncertain write replay, and authoritative replacement readback. These protect operation ownership and stale handles. They do not identify the physical unit after detach. findDevice() still returns the first matching target, so it does not reject multiple JA11 candidates. The current-state report records the permission, rediscovery, and readback boundaries.

9. **Wrong-device threat analysis.**

   | Case | Existing protection | Remaining gap / value of serial |
   | --- | --- | --- |
   | Two JA11 units connected | Attempt binds device name/PID; permission callback and fresh open are attempt-scoped. | Initial and replacement enumeration still select firstOrNull; another candidate is not rejected. Serial equality can help distinguish units only when values differ, but current code does not check cross-device serial uniqueness. |
   | Another FiiO product attaches | VID 0x2972 plus supported PID allowlist rejects other products; a new device cannot satisfy an old attempt’s bound name/PID. | Another supported JA11 with PID 0x0101 or 0x0102 remains plausible and must be counted. |
   | Old UsbDevice or connection reused after detach | Detach closes the session and advances detach generation; open resolves a fresh permissioned descriptor and commits a new generation. | Android’s device name/ID is not a persistent physical identifier. |
   | Stale permission callback | Unique PendingIntent action, request ID, current-attempt check, device/PID check, detach generation, fresh descriptor and permission check. | Serial adds no lifecycle fencing; it can add unit comparison after a valid new session exists. |
   | One JA11 physically swapped for another during reset | A differing nonblank serial is rejected by the Mic/UAC path. | With no serial, a one-for-one swap can be indistinguishable from re-enumeration. Session events alone cannot prove same-unit continuity. The app must never replay the write; readback can only establish state on the returning candidate. |
   | UAC PID changes 0x0102 ↔ 0x0101 | Both PIDs are supported; the restart identity helper removes PID. | A serial match survives this expected mode change. Candidate counting still applies. |
   | Unsolicited detach/reconnect | Without a pending transaction, the repository reconnects a fresh session; it does not resume or replay a write. Generation checks fence old operations. | Treat it as a new session and require a new read/baseline before mutation. |

10. **Identity strength by session type.**

   | Session type | Minimum rule |
   | --- | --- |
   | Initial user-connected session | Supported VID/PID, permission, valid HID interface/endpoints, fresh open, current generation, and exactly one plausible supported JA11 (or an explicit user selection). Serial is not required. |
   | Expected reset with one pending operation | Bind the completed write, control, baseline, old session/device, detach generation, and bounded watchdog. Require the expected detach, exactly one supported replacement, fresh descriptor/permission/open, a new generation, and authoritative readback. Match serial when available; if absent, report only that the requested value is present on the sole returning JA11, not that the same physical unit is proven. |
   | Ordinary later reconnect with no pending operation | Start a new session and read a fresh baseline. No old transaction is inherited; serial is not required. |
   | Multiple plausible devices | Fail closed unless the user explicitly selects one through a supported selection flow. Never choose the first VID/PID match. |

11. **Recommended model: MODEL D.**
   Use different requirements for initial, ordinary, and pending-restart sessions. Do not make serial a prerequisite for general JA11 support. Use operation-bound lifecycle evidence for a single unambiguous expected restart, and use serial as an additional physical-unit match when present. The truthful serialless result is “requested state verified on the sole returning supported JA11”; it must not claim “same physical JA11 verified.” If the product requirement is specifically to prove same-unit continuity despite a possible one-for-one physical swap, Android exposes no equivalent fallback and that stronger claim must fail closed without a matching serial. This policy protects against unintended writes to a replacement: the original write stays bound to the original connection and is never replayed.

12. **Fail-closed conditions under Model D.**
   Stop without replay on an incomplete/uncertain write, cancelled or expired transaction, missing expected detach, stale callback/attempt, unsupported VID/PID, zero or multiple plausible replacement candidates, unavailable permission, failed fresh open/HID claim, unchanged or stale session generation, unstable session observation, serial mismatch when both sessions expose serial, failed or mismatching authoritative readback, or unrelated state changes. A serialless one-candidate readback may establish only the current replacement’s state; if the required claim is same physical unit, classify continuity as unknown and do not report same-unit success.

13. **Minimum production files if implementation proceeds.**
   AndroidKt02h20HidSession.kt (candidate cardinality and selection), FiioJa11DeviceIdentity.kt (separate optional serial match from operation continuity), FiioJa11ControlRepository.kt (transaction-bound serialless replacement path and result semantics), EqLibraryViewModel.kt (truthful result state/message), and FiioJa11Flasher.kt (align Save/Reset correlation; current code compares equal PID and fingerprint minus PID, retaining interface and requiring no serial). AndroidFiioJa11UsbTransport.kt changes only if the chosen identity/result state needs a new transport property. Preserve the current attempt tracker, permission fencing, generation checks, watchdog, cancellation, and no-replay rules.

14. **Automated regressions required.**
   Cover initial and replacement sessions with zero/one/multiple candidates; same serial, missing serial, mismatched serial and duplicate serial across candidates; UAC PID transition both directions; interface changes; late/duplicate/stale permission callbacks; detach during open/commit; unsolicited reconnect with no pending transaction; timeout/cancellation; uncertain write with no replay; exact requested-value and unrelated-state readback; and Flash/Reset Save reconnect behavior. Extend AndroidKt02h20HidSessionTest, FiioJa11DeviceIdentityTest, FiioJa11ControlRepositoryTest, EqLibraryViewModel/watchdog tests, and FiioJa11FlasherTest. No tests were run for this design report.

15. **Whether a descriptor-level physical diagnostic is useful.**
   No, not for deciding the policy. Reading the raw descriptor index might distinguish “no serial descriptor” from “string unavailable,” but either outcome leaves Android without a guaranteed stable unit identifier. J024 already proves both supported high-level serial paths returned null after permission and a successful open. Do not repeat J024 or build a descriptor probe unless a later implementation question depends on that distinction.

16. **Whether another phone window adds information now.**
   No. The current candidate would repeat J024, and phone use cannot resolve the source/history or Android API design question. A future physical window belongs after the chosen operation-bound policy is implemented and its applicable local, emulator, independent-review, and CI gates pass. This report does not authorize or request that window.

**Android evidence:** [UsbDevice](https://developer.android.com/reference/android/hardware/usb/UsbDevice) documents that device IDs are not persistent across disconnects, device names are usbfs paths in the standard implementation, and serial reads can return null or throw without permission. [UsbDeviceConnection.getSerial()](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection#getSerial()) is available only from an opened connection and can return null when not opened; J024 additionally observed null after open. [UsbManager.requestPermission()](https://developer.android.com/reference/android/hardware/usb/UsbManager#requestPermission(android.hardware.usb.UsbDevice,android.app.PendingIntent)) grants temporary permission only until disconnect. AOSP UsbDevice.equals() compares the device name; [UsbHostManager](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/services/usb/java/com/android/server/usb/UsbHostManager.java) removes the old descriptor on detach, and [UsbUserPermissionManager](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/services/usb/java/com/android/server/usb/UsbUserPermissionManager.java) clears temporary permission. The Android API does not promise a globally unique or immutable USB serial.
