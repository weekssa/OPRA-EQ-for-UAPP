Updated 2026-10-05. This record compares the current candidate with mission start source

## Classification: Class B — recovery-state retention across navigation

The mission base already saved `eqResetRunning`, used it to disable Restore defaults, and returned
early from the reset sequence while it was true. The current recovery card and read actions do not
clear that flag, resume its canceled coroutine, restart EQ reset, or issue DEVICE writes. The new
EQ-read callback invokes the existing `HardwareEqRepository.readBlackPearlSnapshot()` path.

The current candidate also adds a `SaveableStateHolder` for the My DAC destination and another for
the Black Pearl DEVICE tab. This preserves the in-flight/recovery UI state while those subtrees are
removed during root or tab navigation. It changes Restore defaults availability relative to the
mission base, whose conditional composition could drop the local saved state on navigation. That is
a functional change to recovery/action eligibility, so the exact candidate is **Class B** under the
mission's literal definition and needs matching physical qualification before merge.

I first removed both holders to return to the mission-base action availability. Independent review
found that this caused the saved operation/review state to disappear silently after tab/root
navigation, contrary to mission §29. Keeping retention is necessary to meet that state-preservation
requirement. The reviewers also confirmed that the read-only snapshot action uses the existing
exclusive-session read path and adds no hardware write or reset replay. The remaining Class B scope
is the extended lifetime of the reset/recovery gate across navigation, not a protocol or mutation
implementation change.
