# 4. NON-NEGOTIABLE PRODUCT TRUTH

## 4.1 EQ Library is not an audio player

EQ Library manages EQ data and bounded hardware transactions.

It does not play PCM audio.

Do not introduce live Android audio-session behavior as part of this UX redesign.

---

## 4.2 UAPP relationship

EQ Library does **not** control USB Audio Player PRO's live Android audio session.

It does not:

- attach `AudioEffect`;
- attach Android `Equalizer`;
- attach `DynamicsProcessing`;
- own UAPP audio-session IDs;
- change Android's active audio route.

The UAPP path is:

`EQ in EQ Library`
→ `review target compatibility`
→ `ToneBoosters-compatible XML`
→ `Android SAF`
→ `user imports file into UAPP`

Saving an EQ to My EQs is not exporting it.

Exporting for UAPP is not applying an EQ to UAPP.

Do not use wording such as:

- Apply to UAPP
- Activate in UAPP
- Live UAPP EQ
- Send directly to UAPP

Use explicit export/import language.

The UAPP target currently accepts up to:

- 10 mapped filters;
- frequency 16–20,000 Hz;
- gain -20 to +20 dB;
- Q 0.1–10;
- established Peak / low-shelf / high-shelf mappings.

Safety headroom comes from source preamp or EQ Library.

Only the established trusted OPRA source-priority path may allow an over-ten-band source to use the first ten filters.

Other sources must be rejected instead of silently truncated or reordered.

Canonical EQ must remain unchanged by export conversion.

---

## 4.3 Canonical EQ

Canonical EQ data is:

- source-neutral;
- immutable;
- device-independent.

Output compatibility, optimization, quantization, generated headroom, UAPP XML, device representations, and hardware presets are derived representations.

Do not rewrite canonical source data merely because a target has different capabilities.

---

## 4.4 Hardware safety sequence

Preserve this model:

`hardware baseline`
→ `local working copy`
→ `edit`
→ `validation`
→ `device-specific quantization`
→ `warnings/headroom`
→ `review`
→ `explicit Apply/Flash/Save operation`
→ `bounded hardware mutation`
→ `required readback/result`

The user must always be able to tell whether they are viewing:

- current/fresh device state;
- last-known stale state;
- a local draft;
- a reviewed candidate;
- an operation in progress;
- a verified result;
- an uncertain/recovery-required state.

Editing must not mutate hardware.

A hardware operation whose completion is uncertain must never be automatically replayed.

Do not add generic `Retry Apply` behavior after an uncertain write.

---

## 4.5 DSP safety

Display graph resolution and final safety-validation resolution are separate concepts.

The existing model may use a faster approximately 96-point frequency grid for display/candidate work.

Final generated-headroom and optimizer acceptance use a dense 12,001-point logarithmic sweep plus exact band centers and nearby samples.

Historical coarse-grid misses included:

- 4.392811513 dB for a +12 dB Q=10 peak;
- 8.683458274 dB for two coincident peaks.

A plausible-looking graph is not the safety oracle.

Do not weaken dense validation.

Do not derive safety/headroom claims from the display graph.

---

## 4.6 No invented DAC support

Current recognized hardware identities are:

- TRN Black Pearl
- FiiO JA11
- exact SIMGOT EW300 DSP

Historical JCALLY JM12 implementation/types do not establish current product support.

Do not expose JM12 or any new DAC based on historical code or similarity.

Do not add new DAC support as part of this UX mission.

Do not declare success just because USB writes completed.

## 9.15 Hardware success

## 9.16 Known hardware failure

- what failed;
- what the device is known to contain.

Do not flatten this into generic `Operation failed`.

## 9.17 Recovery required

Use a distinct high-salience component.

`Device state not verified`

Explain that the operation may have completed and will not be automatically repeated.

Offer the safe next observation, such as:

Do not offer automatic replay.
