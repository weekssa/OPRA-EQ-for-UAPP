# v0.7.0 — draft, not released

Status: software implementation and release-candidate hardening are in progress on
`feature/v0.7-ew300-luna-high` / draft PR #23. No merge, publication, or public EW300 support
claim is authorized.

Current lifecycle recovery source `dea8439956f41cbf83cda314f5f9f53d878c6181` moves EW300 Flash execution out of Compose lifetime and
into the authoritative DAC-session owner. The UI now issues a non-suspending ViewModel event and
observes durable operation-trace state. Automated coverage exercises caller cancellation during
detach, one Save, exact replacement generation/fingerprint, final readback, and uncertain-state
telemetry. The exact signed candidate has passed the complete software/security/signing/install/
launch/publication gates. This is still software evidence only: E033 remains the latest physical
Flash result, and no physical result or public EW300 support claim is inferred.

Scope is the exact SIMGOT EW300 DSP identity (`31B2:0111`, `LE XIAN`, `SIMGOT EW300 DSP`, HID
interface 3) through the existing capability-driven My DAC flow: five-band direct-Hz Peak EQ,
readback, capture, guarded Apply, one-Save Flash, Reset, reconnect-aware verification, and
privacy-safe readable/JSON operation evidence. Playback gain remains device state and is not part
of canonical captured EQs. Additional device controls, firmware, and bootloader operations are
required when the exact hardware profile supports them and protocol safety is established. For
this EW300 fingerprint, those capabilities are not yet evidenced and therefore remain absent from
this release; unknown revisions and VID/PID-only matches remain unsupported.

Accepted historical evidence is recorded in `docs/EW300_VALIDATION_LEDGER.md`. The current branch
fixes a verified permission-flow race by blocking automatic reconnect until the Save send has
completed and by recording permission/Save/readback invariants. Exact signed candidate
`855364e8a9d758f12e7d2a48bdaf89f457e28070` passed the complete software, security, signing,
installation, upgrade/emulator, launch, accessibility, and release-polish gates, but the owner’s
Apply attempt stopped before any write because the editor mapped the EW300 global-gain baseline
incorrectly. Replacement source `8bb87aac689ce28b1e92e115a3f83f1b59ad1f65` corrects that mapping
and passed the complete replacement gate set. A follow-up source
`f41f985cb9f7a5d1622bc2e85ddfe5d14777e25d` blocks automatic reconnect after a pre-Save stop and
also passed the complete replacement gate set. The current source
`7035518b042a7b19c0495869cf247359ee27b4a2` additionally guards queued automatic reconnect at
invocation time and passed the complete replacement gate set. The one consolidated physical session in
`docs/EW300_DSP_HANDS_ON_CHECKLIST.md` observed the expected EW300 re-enumeration and exact
baseline restoration, but the candidate Apply operation telemetry was not exported, so the
end-to-end physical release gate remains incomplete. Latest source
`95e5e3597ce3bc7d3c1011bd0a79e978fc9a6e64` adds the directly tested reconnect-guard seam on top of
the Apply trace boundary; it passed the complete software, security, signing, installation,
emulator, and release-polish gates. No further physical mutation is authorized, so the exact-candidate
hardware gate remains intentionally open.
